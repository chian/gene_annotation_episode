## CONTRACT MISFITS

- new field: api_job_execution completion_target (assignment, number). The completion controller needs its finite target from the commission; the old assignment had none. The parent should send the credit a verified original handoff earns (the episode's `handoff_unit`).
- new field: api_job_execution input_refs (assignment, `record_refs`). The records the service operations read (the subject record and what it names) must be named by the parent: a pass carries only the records named.
- (no new field) `read_from_parent` keeps the commissioner's `message` in the parent input as `message`; the model sees it as `assigned_job`).
- new field: api_job_execution finding (return). Declared form: service, resource_id, handoff_established, qualification, and optional submission_outcome, request_identity, job_identity. The old report had none.
- new field: api_job_execution execution_handoff_refs and new field: api_job_execution execution_completed are required return fields (old: always-present fact sources); every other old fact source is selectable.
- Field names cannot contain a dot: the old fact sources `execution.masking_*` and `execution.blast_utility_*` are returned as `execution_masking_*` and `execution_blast_utility_*`. A parent selecting them must use the underscore names.
- completion credit may pass its target: credit is `handoff_unit` once plus `acquired_record_unit` per acquired record, and the target is the commissioned credit of a verified handoff; operations that acquire records after the handoff push credit above the target and the controller raises `completion_credit_exceeds_target`. The old `api_execution.credit_view` formula is not in the library; the formula in `credit.py` is reconstructed from the intent record (the two positive units of the old configuration) and must be checked by the owner.
- A fact that is a `record_refs` field (for example `execution_blast_database_result_refs`) is filled from the facts the service returns; the system requires the Episode to hold every returned record, so the service's facts may only name records this episode wrote through `ctx.store` (`CustodyError('returned_record_not_held:...')` otherwise).
- `execution_result_origin` (old: object or null; null for the API path) is a `record` field with no null: returned as an empty record.
- The old `api_execution_assignment_v1` carries `subject_ref` as a text reference; custody needs `input_refs` beside it (above).
- The old `report_update` interpretations and the parent-written `x-source` form are not carried (rule 5); the model writes no report.
- The settings the episode reads (`continuation` entry of its binding path): `task_yield_profiles` (`launch_api:<class>` -> `cutoff` as controller cost, `parameters`), `handoff_unit`, `acquired_record_unit`, and optionally `tool_knowledge_directory`, `launch_instructions_directory`.
- The tool is handed no summary: `action` wraps the model's operation arguments in an envelope with the original assignment and `input_refs`, so the tool can read them.

Job episode with five child slots (`launch`, `monitor`, `results`, `hpc_execution`, `hpc_prediction`). ## CONTRACT MISFITS

- BLOCKED-ON-JOB-SERVICE: `job_access`; wanted call: `ctx.services['job_access'].observe_target(target, key=key, resumed=ctx.resumed)`, `.read_file(target, path=path, offset=0, limit=limit + 1, key=key, resumed=ctx.resumed)`, `.write_allocation_control(target, unit_ids=unit_ids, key=key, resumed=ctx.resumed)`, `.observe_queue(configuration, key=key)`, `.run_command(configuration, command, key=key)` (see above).
- BLOCKED-ON-JOB-SERVICE: `estimate_table`; wanted call: `ctx.services['estimate_table'].latest(resource, kind)`, `.observe(...)`, `.history(query, now=now, queue_only=...)`, `.policy()`, `.record(**measurement, key=ctx.operation_key)` and the recorded read `.read('resource_tool_estimates', 'hpc')` (see above).
- BLOCKED-ON-JOB-SERVICE: job ledger handoff record; wanted call: `ctx.store.table(JOB_LEDGER).get(handoff_ref)` read as the execution target (see above).
- new field: hpc_work_planning scope (assignment, `record`): the old code read `context.scope` of the binding context; the owner identity of the ledger carries it, both sisters inherit exactly it, and the received-source scope check needs it. The subjects its `subject_refs` name must also be passed in custody (`validate_scope` reads each subject); no `record_refs` field was added for them (they ride in `received_record_refs` when the commissioner passes them).
- new field: hpc_work_planning received_record_refs (assignment, `record_refs`, optional): the old `context.received_record_refs`: result sources, each source's artifact, and, for a commission source, the source's artifact (`hpc_commission_sources.read` reads it with `get_artifact`).
- new field: hpc_work_planning input_refs (assignment, `record_refs`, optional): the records the planned jobs read; the launch child's `record_refs` and the allocation sister's `input_refs` need them named.
- new field: hpc_resource_prediction scope, received_record_refs; new field: hpc_allocation_execution scope, input_refs (the children's own new fields; this episode fills them in `msg_to_child`: both sisters get this episode's scope and owner episode id; the prediction gets `received_record_refs` = this episode's own received records plus the result sources and artifacts it holds; the allocation execution gets `input_refs`).
- `commission_source_ref` is a `record_refs` field holding exactly one reference in this episode's form and in the prediction sister's form (a form has no single-reference type), and `text` in the allocation sister's form; `commission_id` is `text` (a form cannot enumerate the configured commissions); "exactly one of the two" (the old `oneOf`) is checked in `read_from_parent`. The prediction child's `commission_source_ref` is passed in custody: this episode holds it only if its commissioner named it.
- The sisters disagree on the ledger: the prediction sister expects an `hpc_ledger` service (`open_existing(run_id, owner_episode_id)`), the allocation sister opens `HPCLedger.open_existing(<settings directory>/hpc/<digest(run_id, owner)>)`. This episode creates the ledger at `<settings directory>/hpc/<digest(run_id, ctx.episode_id)>` (the old path with itself as owner), which the allocation sister reads as written; a service for the prediction sister would have to open the same path. The sisters' settings names for the same library directories and yield also differ (`launch_instruction_directory` / `launch_instructions_directory`, `cutoff` / `cost`); this episode uses `launch_instruction_directory`, `tool_knowledge_directory`, `cost`, `parameters`.
- The commission's `yield_bindings['hpc'] = {cutoff, parameters}` cannot reach `yield_controller`: the commission is a Store record or a configured value read by a tool, and `read_from_parent` cannot read it. The controller reads `settings['cost']` and `settings['parameters']` of the run's `continuation` entry instead (old `require_commission_yield` -> `hpc_commission_yield_binding_required:hpc`). Cost zero never stops an accumulating controller; the settings must give a cost above zero.
- Controller choice: accumulation (README 7b: `HPCContinuationEstimator` has no controller of its own). The ledger credit has no declared maximum and no finite commissioned target (obligation credits plus signed model and validation components), so completion and bounded quality do not fit. No "completion credit may pass its target" applies.
- credit: the ledger is outside the Store and `credit` has no services, so the credit is the ledger credit view of the latest tool outcome (`ledger_view`). A unit that commissions a sister changes the shared ledger without reading it back, so `decide` issues `hpc_open` (read the ledger again) after such a unit; the credit of that refresh unit is the sister's gain. If the controller stops right after a sister unit, `completion['credit']` is the credit of the last read; the model identity, accepted obligations and result sources of the return then come from the sister's report (`internal_summary`). Credit is never bounded; the model and validation components are signed and it can decrease.
- `hpc_open` (new tool, not offered to the model) is the initial lookup (the old `state` and `initialize`, which every old tool call repeated). Tool names are the old names with `_` for `.`.
- The old `LaunchReceiptCustody` / report repair, the `redeliver_report` and `wait` actions, `hpc_launch_report_form` and `hpc_report_form` (the forms the old model wrote for child reports) are not carried: a commission has one admitted result, and the parent writes no form. The `launch:<plan_id>` reservation the old `authenticate_launch` wrote into the ledger is not written (a commission has no write); `action` rejects a second launch of a plan and a launch of a closed plan, and the unit journal is the one record of a launch.
- Count/time cutoffs of the old code not carried (README rule 2): the discovery `timeout=90`, the 64 KiB / 8 KiB output truncation (and the `truncated` key), the `[:2000]` slice of the shared history observations and the `min(1.0, ...)` scale of the continuation valuation. `ExecutionMemory.history(..., limit=2000)` keeps its own default inside the library, which this episode does not edit.
- The launch child declares `execution_handoff_refs` and `execution_completed` as selectable fields (the allocation sister's launch child has them required); this episode selects both. The results child's `execution_result_refs`, `execution_result_artifact_refs` and `execution_completed` are selected; the monitor's six `monitoring_*` fields as listed in `task.py MONITOR_SELECTION`.
- The old finding was not typed (the old report had facts only): `finding` is a new typed record (accepted and remaining obligations, model identity, plans frozen and closed, result sources held, credit components, qualification).
- `hpc_work_planning/hpc_runtime.py` (hook-era runtime) was deleted; `gene_annotation_episode/episodic_workflow/root/a107/partner_presence_evidence/tests/test_model_run.py` (the A107 head's hook-era test, another agent's) imports `HPCServices` from it and breaks. `hpc_work_planning/tests/` held two hook-era tests importing it; both deleted.
- No test runs the real runner: a run needs the two declared services and the job records (BLOCKED-ON-JOB-SERVICE). The old tests (six shared check classes over the old runner at `97308b94c`, and two hook-era tests in the working tree) are retired (`retired_tests/a107__partner_presence_evidence__hpc_work_planning.tsv`).

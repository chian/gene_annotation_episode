## BLOCKED-ON-JOB-SERVICE

- BLOCKED-ON-JOB-SERVICE: `job_access` (the run's access to the scheduler and SSH transport; declared in `task.py` `SERVICES = ('job_access', 'launch_instructions')`); wanted call: `await ctx.services['job_access'].exec_command(assignment=assignment, command=command, run_id=ctx.run_id, episode_id=ctx.episode_id, operation_key=ctx.operation_key, resumed=ctx.resumed)`, returning the old factual outcome `{'facts': ..., 'native_outcome': ...}` of one `exec_command` (target resource or coordinator), idempotent on `ctx.operation_key` (a submission whose outcome is uncertain must be found again, not repeated). The library has the transport as `episode_support/acquisition/native_terminal_transport.py::TerminalExecution.execute(state, tool_name, arguments, operation_key)` over a file-backed `PracticalState`; no service wraps it. `task.py job_access(ctx, 'exec_command')` raises `NotImplementedError('BLOCKED-ON-JOB-SERVICE: job_access.exec_command')` when the service does not offer the operation, so every `exec_command` unit raises where it is reached.
- BLOCKED-ON-JOB-SERVICE: the job handoff record kind and the job ledger (LAUNCH_MONITOR_EXTRACT_MECHANICS.md sections 6 and 11, README 5 item 22): the handoff record (job handle, job kind, how to find the job, submission time, launch estimates) is not defined. This episode writes each command receipt as a `source` record (`task.publish_receipt`, provider `episode.practical_receipt`) and returns the receipts whose satisfied `requested_job_handoff` validation qualifies them as handoffs in `execution_handoff_refs`; wanted call: `ctx.store.table(JOB_LEDGER).put({'job': handle, 'event': 'handoff', ...})`.
- Service `launch_instructions`: not a job service. `task.decide` reads `ctx.services['launch_instructions'].read('for_resource', resource)`; the run's caller supplies a zero-argument factory building `LaunchInstructions(directory)` (`episode_support/instructions/launch_instructions.py`).
- Settings the run's `continuation` entry for this binding path must carry: `resource` (the `pbs_ssh` resource configuration), `coordinator_workspace`, `initial_information` (inventory by resource kind), `task_yield_profiles` (`launch_hpc:practical_hpc_handoff` and other request classes: `cutoff`, `parameters`).

## CONTRACT MISFITS

- BLOCKED-ON-JOB-SERVICE: job_access; wanted call: `await ctx.services['job_access'].exec_command(assignment=assignment, command=command, run_id=ctx.run_id, episode_id=ctx.episode_id, operation_key=ctx.operation_key, resumed=ctx.resumed)`.
- BLOCKED-ON-JOB-SERVICE: job handoff/closure records (job ledger); wanted call: `ctx.store.table(JOB_LEDGER).put({'job': handle, 'event': 'handoff', 'at': submitted_at, 'detail': {...}, 'source_ref': reply_ref})`.
- field names: a form field name must be `[a-z][a-z0-9_]*`; 21 old fact-source names contain a dot (`execution.masking_*`, `execution.blast_utility_*`) and cannot be declared under their old name ("Rename nothing" conflicts with the form).
- null: the form has no null type. Old `execution_result_origin` was `object or null` (always null for a launch episode) and the two `*_acquisition` native facts need `empty_facts` of `native_blast_(standard_)database_result_records`, which is not in the library. They are declared selectable (`record`); `final_to_parent` raises `NotImplementedError` when one is selected.
- completion credit may pass its target: it cannot pass it (the target is the total credit of all progress requirements, and credit is the sum of the satisfied ones, both by `math.fsum`), but it may stop short of it: the assignment is complete when its `completion_keys` are satisfied and the last receipt satisfies the endpoint predicate, which can happen while other requirements are open. The old `PracticalYieldEstimator` turned a verified completion into an exact zero forecast (no controller input in the final form, README 5 item 5), and the old `PracticalState` refused any command after completion. Neither is carried: `action` always accepts a command and the controller stops the Episode when the forecast no longer exceeds the cost.
- new field: hpc_job_execution none added. The old child re-read its parent launch's assignment (`_check_parent_inputs`: immutable input versions, masking/utility inputs, native BLAST database job inputs). The child cannot read its parent's assignment (README 5 item 14) and a wrong commission fails in the parent; the parent would have to name those inputs in this assignment (as `record_refs`) for the child to read them. The libraries those checks called (`execution_input_versions`, `native_blast_database_result_publication`, `native_blast_standard_database_result_publication`, `validate_native_job_inputs`) are not in `episode_support/`.
- the old leaf's `execution_handoff_refs` were read through `job_progress_provider.targets._handoff_reader` (a provider, not carried) over records received from the parent; this leaf receives no `record_refs`, so handoffs are the receipts it wrote itself whose satisfied `requested_job_handoff` validation qualifies them. `execution_result_refs` are always empty (a launch episode acquires no results; the old value came from received results).
- the model's output schema is this episode's own flat form (cmd as argv array, env as list of name/value) instead of the A104 `generation_schema`/`decode_response` of `model_exchange/evolutionary_history_evidence/action_transport.py`, which wraps the old selection envelope (tool/reason/wait) that no longer exists.
- baseline validations: the old `PracticalState` froze the initial validations (with a real `checked_at`) at creation; `internal_summary` must be a pure function, so it assesses the initial context with the fixed time `BASELINE_CHECKED_AT`; only the `satisfied` flags enter credit.
- the old `validate_form(form, schema, resolver)` of the A104 `communication` module (JSON-schema report forms with `x-source`) is not called: the typed `RETURN_FORM` is admitted exactly by the system and returned records are checked by custody; `validate_report` keeps the old check that returned facts equal the recorded facts.
- the prompt renderers (`render_hpc_prompt`, `render_selected_execution_prompt`, `render_receiver_prompt`, README 5 item 16) are not in the library: the context travels as the `ModelRequest.context` mapping.

## What it is for (its goal, in its own words)

The A103 launch episode (role `launch`), commissioned by the A103 scientific episode. It picks which permitted
concrete execution request to send to which resource child. `goal.py`:

> "Choose which permitted concrete execution request to commission on an explicit resource_id. Capabilities,
> recorded inventory and timing information inform the choice. Preserve the original job, immutable inputs,
> constraints and pinned instructions. A resource child owns iterative execution in the shared loop. Receive its
> requested typed handoff; no infrastructure chooses an approach. Actual received usable handoff completes this
> launch endpoint with exact zero future credit."

`contracts.py` docstring: "The binding routes a selected concrete assignment. Resource operations and result reads
contain no model, resource selection or investigation loop."

## Task and instructions

`instructions.py` uses the binding instructions (the goal above; `replaces_default_instructions = True`) and adds the
reasoning-commit requirement, tool knowledge, the launch library, the pending_child_delivery repair, the in-process
wait and native events paragraphs, and the exchange-protocol history text. `task.py` (LaunchTask) has the same
decision-loop shape as the scientific task (grain `launch`). `action_policy.py` permits tool, reason, child, wait and
redeliver_report. Under an `hpc` ancestor it permits only tool, child and redeliver_report.

## What it reads from its parent's assignment

`from_parent.py`: `{version: execution_launch_assignment_v1, requests: {<resource_id>: request}, immutable_input_versions, constraints, launch_instructions}`.
Each request is either an API assignment (from `api_execution.assignment_schema(resource_id)`) or a practical
assignment whose `requested_job` is the generic job or one of the native job schemas (BLAST, BLAST masking/utility/
database/standard database, HMMER, HMMER preparation) of that resource. `resource_id`/`resource_kind` are fixed to
the bound resource. A BLAST graded request (`BLAST_GRADED_REQUEST_VERSION`) needs an `ncbi_blast` resource.
`constraints` may restrict `allowed_resource_ids`, `allowed_kinds`, `resource_id` and `kind` (`_permitted`). When the
parent is `hpc`/`hpc_execution`, the launch is authenticated (`hpc_launch_authentication`). Masking/utility inputs,
immutable input versions and native/standard BLAST job inputs are validated against the Store. Initial references:
the masking/utility inputs of each request.

## Decision state and what it shows the model

`decision_state.py` shows the same field set as the scientific task (goal, scope, working_state, visible refs,
credit, evidence vector, credit_binding, time_accounting, pending_work, last outcome/feedback, deliveries,
controller, tools, knowledge, job options, report facts, requested form, current report). It does not add an
annotation context. `internal_summary.py`: the initial context shows execution_resource_capabilities (configured
availability `unknown`, tool names), execution_initial_information, received_bvbrc_values, received_blast_jobs
(with a meaning text: status only as of observed_at, no status request, waiting earns no credit) for annotation
and scientific owners, and received_minhash_values. The decision context shows execution_assignment,
execution_progress (current facts) and selected_execution_task (scientific question and selected tool info from
`services.scientific_parent_task`, each request's job; HMMER jobs through the native profile view).
`decision_inputs.py` adds resource/shared/launch-library/child-option/completed-action/HPC-history/expectation/estimate/native-event/waiting inputs (role `launch`).
`decision_presentation.py` picks the prompt renderer.

## Tools it offers

`operations.py`: `execution.capabilities` (read the caller-bound resource configuration and recorded inventory;
returns the initial decision context). For native BLAST masking/utility result contexts, the catalog is those
families' result operations instead. `internal_summary.resource_tool_contracts` declares the launch, results,
homology-API, native and preparation operations of every bound resource as commission routes. The scientific
parent's tool catalog shows them (`scientific_commission_catalog`).

## How its credit is counted

`credit.py`: kind `operational`. A closed episode returns only its archived view (`closed_credit.py`, receipt prefix
pinned, no repricing). Otherwise a native result family that applies supplies its credit view. Otherwise:
`credit = handoff_unit × (#resource_ids with a usable handoff not already in the initial refs) + acquired_record_unit × acquired_fraction`,
where `acquired_fraction` is fixed at `0.0` in this file. Binding: `execution_received_records_credit_v1`.
Credit is not bounded.

## Continuation (yield estimator and settings)

`yield_estimator.py` (needs `require_private_yield=True`). Each request gets a class: `api_<service>[_<algorithm>][_<database>]_handoff`,
`practical_<resource_kind>[_native_*…]_<handoff|outputs>` or `compact_<version>`. Remaining = (eligible requests
whose resource has no usable handoff in the initial refs) × handoff_unit. If remaining > 0, the controller is
BoundedYieldController(epoch, initial_credit, cutoff of task profile `launch:<sorted classes joined by +>`,
maximum = remaining, parameters). This is the bounded-quality estimator; its maximum is the uncredited request
total. If nothing remains, initial credit must be 0 and a zero-cutoff YieldController is used with an exact-zero
forecast (`launch_original_request_exhaustion_v1`). Settings: `task_yield_profiles` {key: {cutoff > 0, parameters}},
`results_yield_profiles` (native_unbounded_local/hpc), `handoff_unit`, `acquired_record_unit`.
`practical_estimator` = PracticalYieldEstimator(verify_completion).

## What it reports to its parent

`to_parent.py` fact sources: native HMMER families, masking, BLAST utility, UniProt (results), BLAST standard/native
database, HMMER preparation, BLAST pairwise (+ `execution_blast_pairwise_result_refs`), BVBRC appservice and data,
minhash, `execution_handoff_refs`, `execution_result_refs`, `execution_completed`, `execution_result_origin`,
`execution_blast_hsps`, and the BLAST graded return (results role). Facts: a native family's facts, or the received
handoffs/results, file sources and outcomes, origin and completion. `validate_report` requires each x-source field to
equal the recorded facts. Required return source towards the scientific owner: `execution_handoff_refs` when the parent is
gene_context_evidence and an annotation task is required.

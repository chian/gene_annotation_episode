## What this episode is for (its own words)
The episode carries out one assigned API service job (resource kinds `api` / `hmmer_api`, e.g. ncbi_blast, ebi_hmmer, bvbrc_data, bvbrc_minhash, UniProt, BV-BRC AppService), as stated in `goal.py`:

> "Carry out the assigned work through {service} using one selected operation each turn. Keep the original inputs, request, resource and parent constraints fixed. Choose useful preparation, service requests, observations or repair from the actual available operations and received outcomes. Distinguish an immediate returned response from a service job that continues remotely. Preserve the actual request or job identity and submission uncertainty; a missing reply does not establish that no job was created. Establish the requested usable monitoring/results handoff from recorded service facts. The configured controller governs continuation; verified original handoff completion gives exact zero future credit."

## Task and instructions
- `instructions.py` composes the binding goal, tool knowledge, the launch library, the pending_child_delivery repair paragraph and, when wait is permitted, the in-process wait and native_event_targets paragraphs, plus the exchange-protocol history replacement. Unlike HPC and local, it never adds `REASONING_COMMIT_REQUIREMENT`.
- `task.py` is the same iteration loop as the native siblings. Report admission uses grain `launch_api`.

## What it reads from its parent's assignment
- The parent `launch` assignment `execution_launch_assignment_v1`. Each API request is validated by `api_execution.validate_assignment(request, scope=...)`. A BLAST database grader request (`BLAST_GRADED_REQUEST_VERSION`) must target an `ncbi_blast` resource.
- Its own assignment is `api_execution_assignment_v1` (service, subject_ref, algorithm, database, parameters, page_size) or `api_service_assignment_v1` (service, request, endpoint, constraints).
- `prepare_assignment` additionally runs `api_execution.validate_assignment(selected, scope)` and `_validate_blast_launch_selection(original, selected, scope)`. `_check_parent_inputs` also runs `_validate_blast_api_parent_request`.

## Children
None (`APIJobChildEligibility`: no child roles, no allowed children).

## Decision state and what the model sees
- It uses the same `decision_state` field set as the native siblings. `decision_context` is its own: `execution_assignment`, `execution_progress` = its own `facts(context, {})`, any `api_execution.decision_context`, and `selected_execution_task` from the scientific parent. For API requests, `selected_execution_task` is built only for service `ebi_hmmer`.
- `initial_decision_context` holds execution_resource_capabilities (with `api_configuration_facts`: ncbi_contact_configured and provider_rate_state_configured booleans), execution_initial_information and received_bvbrc_values. For annotation or gene_context_evidence roles it also holds received_blast_jobs with their meaning text and received_minhash_values.
- Its own prompt (`decision_presentation.py`, 413 lines; HPC and local have 59) has two parts. TASK: scientific QUESTION, assigned job, assigned scope, selected API work, parent constraints, parent-selected tool guidance, configured resource, exact assigned scientific request, execution method and decision rules, each callable operation with its instructions and argument schema, selected resource instructions, information requested by the parent, the requested JSON return and the meanings of the requested recorded facts. STEERING: completed action reports, pending child delivery, own action categories table (completed, observed signed yield, expected next yield, uncertainty, uncompleted attempts), current operational continuation (turns, credit, expected next gain, uncertainty, continuation cost, controller decision), yield information limits, original handoff completion, recorded own API outcomes and complete API errors, latest own action, feedback, own pending work, and lookup results. `select_profile_api_execution_values` keeps validated scientific API operands literal before generic masking. The renderer selection is `render_api_job_prompt`, which picks between the HPC, gene-context, API-launch, selected-execution, monitor and receiver renderers.

## Tools offered
- These are the API service operations from `api_execution.operation_contracts(resource_id, 'launch_api')` and `catalog`, the native masking or utility result catalogs when those families apply, and the homology API contracts.
- Common actions are `tool` only. When the assignment is `api_service_assignment_v1` (a remote service job), they are `tool` and `wait`.

## Credit
`operational`. It returns the closed view if one exists, otherwise a native result family view, otherwise `api_execution.credit_view(context, receiver_selection)`. Completion falls back to `api_execution.verify_completion`. Credit is not bounded.

## Continuation
Profile key `launch_api:` + request yield class. For API requests the class is `api_<service>[_<algorithm>][_<database>]_handoff`. The controller was YieldController + PracticalYieldEstimator(`verify_completion`), where verified handoff completion gives exact zero future gain. This maps to the completion-with-a-target estimator.

## Report to parent
Fact sources match the native siblings without the terminal practical facts, and add the BLAST grader return source (`BLAST_GRADED_RETURN_SOURCE`, for results with ncbi_blast). Facts are `api_execution.facts(...)` with `execution_result_origin: None`. `validate_report` checks the masking and utility returns, the UniProt closed facts when requested, and x-source equality with recorded facts.

## Differences from siblings
It has its own goal text, its own TASK/STEERING prompt, wait for service jobs, no reasoning-commit paragraph, the API validation path, and facts and credit from `APIServiceExecution`. `terminal_execution.py` here is a single-file copy of the terminal behaviour, imported only for `operation_catalog` and `TerminalExecutionBehavior` in contracts. The API path does not use it.

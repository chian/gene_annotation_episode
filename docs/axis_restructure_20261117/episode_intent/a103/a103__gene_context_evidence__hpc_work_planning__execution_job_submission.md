## Purpose (goal, in its own words)

`goal.py` `LaunchGoal.instructions`:

> Choose which permitted concrete execution request to commission on an explicit resource_id. Capabilities, recorded inventory and timing information inform the choice. Preserve the original job, immutable inputs, constraints and pinned instructions. A resource child owns iterative execution in the shared loop. Receive its requested typed handoff; no infrastructure chooses an approach. Actual received usable handoff completes this launch endpoint with exact zero future credit.

So this episode is a dispatcher: it receives a launch assignment listing one concrete request per configured resource, picks which permitted request(s) to commission to a resource child (API, local or HPC), and finishes once a usable typed handoff has come back. It does not run jobs itself.

## Task and instructions

- `instructions.py` builds the instructions from: the binding's goal text, plus `REASONING_COMMIT_REQUIREMENT` when `reason` is permitted, the tool-knowledge instructions when `tool_knowledge` is in context, the launch-instruction-library instructions when `launch_instruction_library` is in context, and then these episode-specific paragraphs:
  - the pending_child_delivery repair text (select `redeliver_report` with a corrected form, use only saved child facts, preserve `current_report_update`, no new scientific work);
  - when `wait` is permitted: the `pending_child_` handle text (wait with that handle, event `returned`, `after_cursor 0`, `reconsider_at null`; waiting earns no scientific credit);
  - when native event information exists and wait is permitted: the `native_event_targets` paragraph (registration is metadata, not proof of submission; `state_changed` is not result readiness; no credit from passing time);
  - under the exchange protocol, the old history guidance is replaced with: "Use request_context exchanges for your own attempt metadata and selected inputs... Read exact previously received outcomes with the ordinary episode.history tool, view=records and selected decision_indices...".
- `task.py` (`LaunchTask`) is the per-decision loop: build decision state, build the action schema (`library.action_contracts.action_schema` through `private_policy_call`), call the model, admit the response, record effects, execute the selection, compute credit, return a controller value. Episode-specific parts of the admission:
  - a `reason` selection whose commit is all empty lists is rejected as `empty_reasoning_commit` unless the binding's `reasoning_has_task_content` says otherwise or `evidence_processing.kind == 'no_applicable_evidence'`;
  - a failed `job_child` (OSError/sqlite/subprocess/AcquisitionError) becomes feedback `category: job_assignment` with code `job_storage_failed` / `job_control_failed` / `job_operation_failed` and the role and `job_ref`;
  - `closed_top_level_form_required` gets the repair text "schema_json must encode a JSON Schema object with the explicit top-level field "type": "object" ...";
  - `component_native_return_channels_required` feedback carries `required_fact_sources` and `repair`;
  - for an `episode_child` role `results` with `execution_results_assignment_v1` and selector `bvbrc_minhash_result_selector_v2`, ContractError detail keys (`source_ref`, `artifact_ref`, `handoff_ref`, `pair_metadata_index`, `row_index`, `genome_id`, `field`, `record_path`) are returned as `input_detail`;
  - for a `reads.map` tool ValidationError, the `read_mapping.parameter_schema_failure` feedback is added;
  - report updates are validated with `grain='launch'` against `job_assignment`; a delivery-resolution response must keep `report_update` equal to the current interpretation;
  - after an observed `shared.read_information` tool action, shared grading results are retained.
  - `_validate_hpc_launch_report_contract = validate_hpc_launch_report_contract` (from `library.hpc_handoff_report_contract`) is attached to this task class only (absent in the three children).

## What it reads from its parent's assignment

`from_parent.py` `LaunchAssignment`:
- Assignment schema (`assignment_schema`): `{version: 'execution_launch_assignment_v1', requests: {<resource_id>: launch_request_schema(...)} (minProperties 1, no extra keys), immutable_input_versions: [INPUT_VERSION_SCHEMA], constraints: object, launch_instructions: SELECTION_SCHEMA}`.
- Each request schema: API resources use `api_execution.assignment_schema(resource_id)`; local/HPC use `ASSIGNMENT_SCHEMA` (practical assignment) with `resource_id` const, `resource_kind` const, and `requested_job` = anyOf generic + `requested_job_schemas` + `preparation_job_schemas` for that resource.
- `prepare_assignment`: when the commissioning parent role is `hpc`/`hpc_execution`, `hpc_launch_authentication.authenticate_launch` runs first; then `_launch` validation, masking/utility input checks per request, immutable input versions, and native BLAST database / standard database job input validation.
- `_launch`: a request with `BLAST_GRADED_REQUEST_VERSION` must match `BLAST_GRADED_REQUEST_SCHEMA` and be bound to an `ncbi_blast` service (`blast_database_grader_resource_conflict`); other requests are validated per resource (`execution_resource_not_bound`, `execution_resource_identity_conflict`, `execution_resource_kind_conflict`, workspace confinement, operation-level `validate_assignment`); constraints `allowed_resource_ids` / `allowed_kinds` must be lists of non-empty strings.
- `_permitted`: a resource is permitted when it is in `requests` and satisfies `allowed_resource_ids`, `allowed_kinds`, `resource_id`, `kind` constraints.
- `required_return_sources`: when this episode's parent path ends at `gene_context_evidence` and `services.annotation_task_required()` is true, the launch return must include `execution_handoff_refs`.
- `initial_references`: for `launch`, the masking and utility input references of every request.

## Decision state and what it shows the model

`decision_state.py` builds the context (inside a store read snapshot): goal, scope, working_state, `visible_record_refs` (references found in working state, last outcome, visual evidence, current report and child report forms), `current_credit` (or the root annotation-axis credit form when `mode == 'annotation_axis_credit'`, in which case working state is emptied, controller is reduced to `arms, annotation_credits, root_score, decision`, and a previous child action outcome is reduced to counts), `current_evidence_vector`, optional `investigation_progress`, `credit_binding`, `time_accounting`, `pending_work`, `last_local_outcome`, `feedback`, `visual_evidence` (last completed `image.view`), `report_deliveries`, `controller`, `controller_binding`, `tools`, `tool_knowledge`, `job_episode_options`, `available_report_facts`, `requested_report_purpose`, `requested_form`, `current_report_update`, `current_report_basis_refs`, `report_lifecycle` ("Interpretations are the last actual reasoning basis; later tool outcomes are facts, not a new judgment."), monitoring credit when present, the binding's own `decision_context`, and `_completed_work_axis_results`.

The binding's own decision context (`internal_summary.py`): `execution_assignment` and `execution_progress` (= this episode's facts), plus `selected_execution_task` when `services.scientific_parent_task(context)` returns a parent task and every request is either an `ebi_hmmer` API request or a local/HPC request naming exactly one supported native job (`native_blast`, `native_blast_masking`, `native_blast_utility`, `native_blast_database`, `native_blast_standard_database`, `native_hmmer`, `native_hmmer_preparation`; HMMER jobs shown through `native_profile_scientific_job_view`). The selected task carries the scientific question, the parent's selected tool info, the requests with resource information, constraints and selector.

Initial decision context (`initial_decision_context`): `execution_resource_capabilities` (per resource: id, kind, availability `unknown`, tool names, workspace/policy/account/python_executable/service/base_url, inventory snapshot, API configuration facts `ncbi_contact_configured` / `provider_rate_state_configured`), `execution_initial_information`, `received_bvbrc_values`; for roles `annotation`/`gene_context_evidence` with `ncbi_blast`, the received BLAST jobs (axis summaries for `annotation`) with the long `received_blast_jobs_meaning` text; received MinHash values when forwarded.

`decision_inputs.py` adds: `resource_context`, `shared_information_context`, `launch_instruction_library`, `selected_launch_instructions`, `child_options` text, the registry's initial binding context (field conflict raises), `completed_action_reports` (unless literature or annotation-axis mode), `requested_action_history` in HPC contexts, `pending_work`, `execution_expectations` for role `launch` (with `job_execution_options` when search modes are configured), `resource_tool_estimates`, `native_execution_expectations`, `native_event_targets`, `waiting_support`, `contract_information_profile`.

Presentation (`decision_presentation.py` `present_launch_task`): picks a text renderer by context type in this order: HPC prompt, published-scientific (gene_context_evidence) prompt, API launch prompt, selected-execution prompt, monitor prompt (unless native profile receiver), else receiver prompt; tracks per-(episode, role) prompt state across `decision_bootstrap` / `decision_update` / `decision_lookup_result` frames; untasked contexts are sent as JSON.

`decision_delivery.py`, `decision_exchange.py`, `saved_decision_exchange.py`, `decision_contracts.py`, `decision_provider.py`: the model call and the request_context/select_action exchange (lookups: `child_options`, `composition_information`, own attempts), replay validation of saved requests, and provider dispatch with role `REASONING` and this binding's prompt renderer. These are generic loop machinery repeated in every episode; the only episode-specific content is the renderer and instruction composer.

## Tools it offers

`operations.py` / `contracts.py`: one own operation, `execution.capabilities` — "Read the actual caller-bound resource configuration and already recorded inventory; no discovery or selection." (empty input). Executing it returns the initial decision context as a completed outcome; argument or reference errors return `invalid` with the error code. For a results context that is BLAST masking/utility, the catalog is that result family's catalog instead. `resource_tool_contracts` declares, per configured resource, the child launch operations (API operation contracts, or `exec_command` for local/HPC) and result operations (`execution.results.status`, `.collect`, `.read`), homology API contracts, and native/preparation operation contracts, each with an `invocation_route` of kind `commission` naming entry role, resource and resource role — the model sees which child would run them.

Action policy (`action_policy.py`): `('tool', 'reason', 'child', 'wait', 'redeliver_report')`, but only `('tool', 'child', 'redeliver_report')` when any ancestor role is `hpc`.

## Credit

`credit.py` `ExecutionEpisodeCredit`: kind `operational`. Credit is the closed view if this episode has a closed credit snapshot (`closed_credit.py`), else live: if a native result family applies, that family's credit view; otherwise
`credit = handoff_unit * new_handoff_count + acquired_record_unit * acquired_fraction`, where `new_handoff_count` = number of distinct resource_ids with a usable handoff among received handoffs, minus those already in the initial known refs; `acquired_fraction` is fixed at 0.0 here. Binding record `execution_received_records_credit_v1`, qualification `original_request_resource_scope_selector_and_actual_received_unique_information`. Unbounded (no clamp).

`closed_credit.py`: at closure, captures the projected view into the closing facts under `execution_closed_operational_credit_v1` with digests of context, binding record, completion, archive, observation history and receipt prefix; later reads return only that saved view and check it has not changed.

`completion.py`: completion proof for an action is either a native result family's proof or `practical_completion_v1` built when an own completed action's record refs include a usable handoff (`endpoint: usable_handoff`, `validation_keys: ['received_usable_handoff']`); `verify_completion` reuses a single recorded matching observation for a closed episode.

## Continuation (yield estimator and settings)

`yield_estimator.py` `_launch_yield_controller` (requires `require_private_yield=True`): eligible = permitted requests; already_received = resource ids with usable handoffs in the initial known refs; `remaining = len(eligible - already_received) * handoff_unit`.
- If remaining > 0: profile key `'launch:' + '+'.join(sorted(request classes))`, where a request class is `api_<service>[_<algorithm>][_<database>]_handoff`, `compact_<version>`, or `practical_<resource_kind>[_<native...>]_{handoff|outputs}`; uses the old `BoundedYieldController(epoch, initial_credit, profile['cutoff'], remaining, YieldParameters(**profile['parameters']))` — continuation bounded by the uncredited request slots.
- If none remain: initial credit must be 0, and an exact-zero `YieldController` (`launch_original_request_exhaustion_v1`) raises if any history value is non-zero.
- Settings: `task_yield_profiles[<key>] = {cutoff > 0, parameters}`; a missing key raises `execution_original_task_yield_profile_required:<key>`.
- In the new layout this corresponds to the completion-with-a-target estimator (target = remaining request slots × handoff_unit, exact zero once every eligible request is handed off). That mapping is inferred here, not written in the old code.

## What it reports to its parent

`to_parent.py` `LaunchReport.fact_sources` (role-dependent): native HMMER sources, masking/utility sources, standard/native BLAST database sources, HMMER preparation, BLAST pairwise sources + `execution_blast_pairwise_result_refs`, AppService sources, BV-BRC data sources, MinHash sources, and always `execution_handoff_refs`, `execution_result_refs`, `execution_completed`, `execution_result_origin`, `execution_blast_hsps` (with the meanings given in the file). `facts` (live): `execution_handoff_refs` (sorted received usable handoffs), `bvbrc_appservice_support_refs`, `execution_blast_hsps: []`, `execution_result_refs`, `execution_file_source_refs`, `execution_file_capture_outcomes`, `execution_result_origin`, `execution_completed` (any handoff readable as complete), with empty lists for every native family; plus closed-credit facts. `validate_report` checks masking/utility/UniProt returns and requires every `x-source` field to equal the recorded fact (`execution_report_disagrees_with_recorded_facts`). `report_delivery.py`: without a report contract, returns `{credit, pending_handles, current_report_facts}`; with one, returns the saved form or builds it with `form_with_facts` and saves facts + interpretations.

`received_information.py`: for roles `annotation`/`gene_context_evidence`, the received-report sources and facts of each result family are forwarded (file capture, masking, utility, UniProt, BLAST database families, HMMER preparation, BLAST pairwise, BV-BRC data, MinHash, AppService and its homology/phylogeny/alignment/genome alignment/proteome/comparative systems/fastqutils/application returns; overlapping fact names raise `received_report_fact_conflict`).

## Configuration

`configuration.py` `LaunchConfiguration(services, store, directory, run_id, resources, initial_information, tool_registry, handoff_unit, acquired_record_unit, log_window_bytes, log_roles, require_private_yield=False, results_yield_profiles=None, task_yield_profiles=None)`: resources must be non-empty with kinds in `KINDS`; initial information only for bound resources; both credit units finite and > 0; `log_window_bytes >= 1`; results profiles only `native_unbounded_local` / `native_unbounded_hpc`; native resource keys limited to the seven native job families (else `a103_execution_resource_binding_conflict`). It builds one `TerminalExecutionBehavior` per non-API resource, one `APIServiceExecution` for all API resources, an `ExecutionProgressProvider`, `LocalFileSourceResults`, binds itself as execution owner in the tool registry, and installs the primary and preparation result readers. `binding_record.py` records `binding_id` = this path, `VERSION = 'execution_episode_v1'`, and the configuration.

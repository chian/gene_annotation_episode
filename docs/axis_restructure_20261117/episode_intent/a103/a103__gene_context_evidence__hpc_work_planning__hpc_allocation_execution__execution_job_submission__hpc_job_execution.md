## What this episode is for (its own words)
The episode is the execution agent for one actual HPC (PBS-over-SSH, kind `pbs_ssh` mapped to `hpc`) job that its parent already authorised. The goal text comes from `terminal_goal.py`:

> "You are the execution agent for the actual job and resource assigned below. Use exec_command to write and run the shell code needed for that job. Choose scripts, environment preparation, software invocation and recovery from the actual resource instructions and observed results. No sequence of setup or job-stage operations is prescribed. Preserve the caller's scientific inputs, desired outputs and acceptance criteria. Historical inventory is context, not proof of present usability. Each command is one ordinary episode action: its actual result and earned credit enter the iterator, including failure or zero progress. Host bookkeeping records command versions and actual native job identities; do not maintain a parallel receipt ledger. If a submission outcome is uncertain, investigate that original submission rather than create a duplicate. Use the provided resource-specific instructions, account, storage and existing authentication route. ... target=resource runs on the assigned resource; target=coordinator runs in the local run directory for supplied-input and transport work. ... For coordinator-side transfers, execution_resource.ssh_argv, when present, is the exact configured transport prefix. ... The episode iterator decides continuation from credit; add no stopping budget."

It then adds "Resource instructions supplied from the frozen library" for this resource (`launch_instructions.for_resource`).

## Task and instructions
- `goal.py` hands off to the terminal goal of the per-resource `TerminalExecutionBehavior` (`_delegate(context).instructions`).
- `instructions.py` adds, in order: the binding goal; `REASONING_COMMIT_REQUIREMENT` if `reason` is permitted (it is not: action policy is tool only); tool knowledge; the launch instruction library; the pending_child_delivery / `redeliver_report` repair paragraph; the in-process wait paragraph and the native_event_targets paragraph when wait is permitted (not for this role). Under the decision-exchange protocol, the "fresh provider conversation" history guidance is replaced by the request_context / `episode.history` guidance.
- `task.py` is the iteration loop: one model decision, one selected action, its result and credit go into the iterator. Invalid selections are recorded as `rejected` with feedback (schema diagnostic, closed top-level form repair text, `component_native_return_channels_required` repair, MinHash selector input detail, `reads.map` parameter diagnostics). A model-call failure ends the source as `source_failed`. Report admission uses grain `launch_hpc`.

## What it reads from its parent's assignment
- The parent is a `launch` episode whose assignment is `execution_launch_assignment_v1`: `requests` (one per resource id), `immutable_input_versions`, `constraints` (allowed_resource_ids, allowed_kinds, resource_id, kind), `launch_instructions` (`parent_launch_contract.py`).
- HPC-only difference (`from_parent.child_assignment_schema`): when the parent is `launch` and an ancestor in the path is `hpc`, the child assignment schema is an `enum` of exactly the parent's already-permitted HPC requests ("A frozen HPC launch exposes only its already authorized request"); with no such request it raises `frozen_hpc_launch_request_missing`. Local and API siblings do not have this.
- Its own assignment is `practical_assignment_v1` (ASSIGNMENT_SCHEMA from practical_execution_records) with `resource_id`, `resource_kind` = `hpc`, `workspace` (confined to the resource workspace), `requested_job` (generic or a native family: native_blast, native_blast_masking, native_blast_utility, native_blast_database, native_blast_standard_database, native_hmmer, native_hmmer_preparation), `endpoint` (`usable_handoff` or `completed_job_outputs`), `initial_context`.
- `prepare_assignment` / `_check_parent_inputs` re-validate against the parent's recorded launch request: masking and utility inputs, immutable input versions, native and standard BLAST database job inputs.

## Children
None. `child_roles` and `allowed_children` return `()`. It is a leaf.

## Decision state and what the model sees
`decision_state.py` builds: goal, scope, working_state, visible_record_refs, current_credit, current_evidence_vector, credit_binding, time_accounting, pending_work, last_local_outcome, feedback, visual_evidence, report_deliveries, controller state and binding, tools, tool_knowledge, job_episode_options, available_report_facts, requested_report_purpose, requested_form, current_report_update, current_report_basis_refs and report_lifecycle ("Interpretations are the last actual reasoning basis; later tool outcomes are facts, not a new judgment."). It then adds the binding's `decision_context`. For this episode (via `terminal_summary.py`) that is execution_assignment, execution_resource (workspace, kind, policy, account, ssh_argv, python_executable, scheduler, inventory_snapshot), coordinator_workspace, execution_progress and execution_completion. `initial_decision_context` adds execution_resource_capabilities, execution_initial_information and received_bvbrc_values.
`decision_inputs.py` adds: resource_context, shared_information_context, launch_instruction_library, selected_launch_instructions, child_options, completed_action_reports, `requested_action_history` (HPC prompt context only), pending_work, execution_expectations captured for `launch_hpc` (with job_execution_options when search modes are configured), resource_tool_estimates, native_execution_expectations, native_event_targets, waiting_support.
`decision_presentation.py` renders with `render_hpc_prompt` when the state is an HPC context. Otherwise it uses the published gene-context, API-launch, selected-execution, monitor or receiver renderer.

## Tools offered
- `exec_command` (from terminal_contracts.py): `cmd` (string or argv), `workdir`, `env` (required), `target` = `resource` (default) or `coordinator`. Every command is journalled and the PracticalState records a receipt with validations against the assignment's endpoint predicates.
- The binding also declares resource tool contracts for its parent's catalogue (`internal_summary.resource_tool_contracts`): the launch catalogue, `execution.results.status|collect|read`, and the native and preparation operation contracts.
- Only the common action `tool` is offered (`action_policy.py`).

## Credit
`credit_kind` = `operational`. `credit.project_credit` returns the closed operational credit view when the episode already closed (closed_credit.py: captured in the closing facts as `execution_closed_operational_credit_v1`, never re-priced). Otherwise it uses the credit view of the matching native result family (masking, utility, standard database, database, HMMER preparation, BLAST, HMMER). Failing those, it uses the practical terminal state's `credit_view()`. Completion uses the family proof or the practical state's `completion_proof`, and `verify_completion` checks it. Credit is not bounded.

## Continuation
`yield_estimator.py`: requires `require_private_yield=True` and uses the profile `task_yield_profiles['launch_hpc:' + request_yield_class]`, where the class is `practical_hpc_<native families>_<handoff|outputs>`. A missing profile raises `execution_original_task_yield_profile_required`. Each profile is `{cutoff > 0, parameters}`. The old controller was `YieldController(epoch, initial_credit, cutoff, YieldParameters(**parameters), estimate_with_context=PracticalYieldEstimator(verify_completion))`, which gives exact zero expected gain once completion is verified. In the new layout this is a completion-with-a-target estimator, with the target being verified completion of the requested endpoint.

## Report to parent
`to_parent.py` fact sources: the native HMMER, masking, utility, standard and native BLAST database, HMMER preparation and BLAST pairwise families; BV-BRC data; MinHash (when configured); the terminal practical facts (`practical_completed`, `practical_receipt_digests`, `practical_receipt_refs`); `execution_handoff_refs`; `execution_result_refs`; `execution_completed`; `execution_result_origin`; and `execution_blast_hsps`. Facts are the terminal facts plus handoffs read from the practical receipt refs, result refs, file source refs and capture outcomes, origin and `execution_completed`. `validate_report` requires every x-source field to equal the recorded facts. The form is saved once with the facts and interpretations (`report_delivery.py`).

## Differences from siblings
- Compared with local_job_execution, these parts are identical apart from the role name: task, credit, closed credit, completion, presentation, terminal_* and to_parent. HPC adds the frozen-HPC child assignment schema. HPC `internal_summary` does not add `selected_execution_task`; local does.
- Compared with api_job_execution: HPC has split `terminal_*.py` files and an `exec_command` tool. API delegates to `APIServiceExecution`, has its own goal text and prompt renderer, and offers wait for service jobs.

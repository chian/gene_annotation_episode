## Purpose (goal, in its own words)

Role `results`. It is not an entry role, and it replaces the default instructions. From `goal.py`:

> Acquire the original selected execution results through the original handoff. Choose bounded status or requested
> file/page reads using actual preceding outcomes. Preserve partial bytes and native scores. Native paths expose the
> current resource filesystem: the exact attempt observation does not establish that current file bytes were produced by
> that attempt. Separate read windows are not an atomic file snapshot. The scientific parent interprets the returned
> records. Original work, resource and selector stay fixed. Only actual complete acquisition establishes this endpoint.

## Task and instructions

`instructions.instructions` composes the instructions. Because `replaces_default_instructions = True`, the goal replaces the A-root
`INSTRUCTIONS`, or the job-episode instructions for a job source. It then appends:
- `REASONING_COMMIT_REQUIREMENT`, when reason is permitted;
- the tool knowledge and the launch-instruction library;
- the pending-child-delivery repair text;
- the in-process wait text, when wait is permitted;
- the native-event text, when native event information exists and wait is permitted.

Under `decision_exchange_v1`, the old history paragraph is replaced by the request_context guidance.

`task_action.py` handles these selections:
- `reason`, through the specialist's `execute_reasoning` or `store.commit_reasoning`;
- `wait`;
- `tool`.

It also has these extra behaviours:
- `automatic_score_updates` after a non-wait outcome;
- `retain_shared_grading_results` after `shared.read_information`;
- `job_child` storage/control failure feedback;
- `reads.map` parameter-schema feedback.

## What it reads from its parent's assignment

The assignment is `execution_results_assignment_v1` (`result_records.RESULTS_SCHEMA`): `handoff_ref` and `selector`. The selector carries
conditional schemas for `local_file_source_selector_v1` and the per-family result selectors (`result_selector_conditions`).

`prepare_assignment` does the following:
1. It restores a recorded returned commission (`saved_commission`) when the parent's receipts show the same child, assignment and scope.
2. It resolves the target: a retained masking or utility target, or else the handoff target from `ExecutionProgressProvider.targets`.
3. It validates the selector for that target family (`selector_contracts._selector`). Generic native paths must be confined to the
   target workspace.
4. It validates family-specific selected inputs: local file sources, masking, utility, standard and native BLAST databases, and BV-BRC data.

## Tools

The tools come from `work_operations.catalog` and are routed by target family:
- generic local or PBS targets: `execution.results.status`, `execution.results.collect` and `execution.results.read` (path, offset, and a
  limit of at most 1 MiB), from `result_operations`;
- native BLAST masking and utility, standard and native BLAST database, HMMER preparation, HMMER and BLAST: each family's own
  `operation_catalog`;
- API targets: `api_execution.catalog`.

Errors become `invalid` outcomes, except retained-artifact custody failures for local file sources, which raise. The common actions are
tool, plus `wait` for an `api_service_assignment_v1` API target.

## Credit

The credit kind is `operational`. `project_credit` returns the frozen closed view when one exists (`closed_credit`: "later delivery never
reprices it"). Otherwise it returns the live view:
- each family delegates to its own credit_view (masking, utility, standard and native database, HMMER preparation, BLAST, HMMER, API);
- for generic native results: `credit = acquired_record_unit × (mean over requested paths of the newly covered byte fraction)`. This is the
  union of byte positions, excluding windows in the initial refs. Binding `execution_received_selector_coverage_credit_v2`, qualification
  "original_selector_byte_position_union_current_filesystem_version_unverified";
- for mixed local-file sources: the acquisition counts × `acquired_record_unit` (binding `execution_received_records_credit_v1`).

`handoff_count` is fixed at 0 in Results. The credit is not bounded, although the generic fraction is naturally at most 1 per path.

## Continuation

The private yield applies only when `require_private_yield`. It is chosen per target:
- **Native target, finite generic selector.** Profile `task_yield_profiles['results:native_finite_<kind>']`. `remaining =
  acquired_record_unit × (1 − originally covered fraction)`. The estimator is: the verified completion endpoint (PracticalYieldEstimator);
  else exact zero when nothing remains; else `estimate_bounded_credit_yield(maximum_credit=remaining)`.
  - Closest current equivalent: **completion with a target**, where the target is the remaining uncredited bytes, with the verified
    endpoint giving exact zero.
- **Native target, unbounded window.** Profile `results_yield_profiles['native_unbounded_<kind>']` with a plain controller.
  - Closest: **accumulation**.
- **API or typed selector.** Profile `results:api_<service>[_<selector version>]` or `results:typed_<kind>_<selector version>`, with
  `PracticalYieldEstimator`.
  - Closest: **completion with a target**.

Settings: `cutoff` > 0 and `parameters` (YieldParameters) per profile.

## Report to parent

`to_parent.facts` = `_live_facts` + `_closed_credit_facts`. The live facts are:
- the per-family native facts;
- or, for API targets, the API facts, with `BLAST_GRADED_RETURN_SOURCE` rows when the target needs a BLAST grader;
- or the generic facts: `execution_handoff_refs`, `execution_result_refs`, `execution_file_source_refs`, `execution_file_capture_outcomes`,
  `execution_result_origin` (NATIVE_RESULT_ORIGIN qualifications), `execution_completed`, `execution_blast_hsps` and
  `bvbrc_appservice_support_refs`.

Empty family sources are always present. `validate_report` checks masking and utility received reports and UniProt frozen facts, and
requires every x-source field to equal its fact. `required_return_sources` is `execution_result_refs` under an annotation-task parent.
`received_parent_records` forwards the file, masking, utility, UniProt, BLAST, BV-BRC and AppService sources to annotation-role receivers.

## Differences from similar episodes

- The Launch episode (`hpc_allocation_execution/execution_job_submission`) shares the configuration operands, the closed-credit rule,
  `protected_reference_access` and `terminal_validation` (identical). Its goal, credit (handoffs, not bytes), yield (bounded remaining
  handoffs) and children all differ.
- `api_acquisition`/`hmmer_acquisition`/`appservice_*` and the seven `native_*_result_acquisition` modules are acquisition engines
  that live in this episode's folder. Launch builds `APIRecordAccess` directly. Its `native_result_owner` names the Results episode under
  the HPC parent (`.../hpc_allocation_execution/execution_result_acquisition`), not this one. This episode's own progress provider names
  itself (`.../hpc_work_planning/execution_result_acquisition`) and imports `APIObserver` from the sibling
  `hpc_work_planning/execution_progress_assessment`.
- Compared with the monitor: Results has `reason`, `automatic_score_updates` and shared grading retention, and no children.

## What it is for (its goal, in its own words)

`goal.py` delegates to `native_goal.py`:

> You are the execution agent for the actual job and resource assigned below. Use exec_command to write and run the
> shell code needed for that job. Choose scripts, environment preparation, software invocation and recovery from the
> actual resource instructions and observed results. No sequence of setup or job-stage operations is prescribed.
> Preserve the caller's scientific inputs, desired outputs and acceptance criteria. Historical inventory is context,
> not proof of present usability. Each command is one ordinary episode action: its actual result and earned credit
> enter the iterator, including failure or zero progress. Host bookkeeping records command versions and actual native
> job identities; do not maintain a parallel receipt ledger. If a submission outcome is uncertain, investigate that
> original submission rather than create a duplicate. Use the provided resource-specific instructions, account,
> storage and existing authentication route. workdir and env apply to the selected command only. target=resource runs
> on the assigned resource; target=coordinator runs in the local run directory for supplied-input and transport work.
> Both are ordinary journaled actions; resource computation belongs on its actual allocation. For coordinator-side
> transfers, execution_resource.ssh_argv, when present, is the exact configured transport prefix. Append the remote
> shell command as its final argument and preserve stdin. The supplied configuration gives the existing connection
> details. target=resource uses that transport directly. The episode iterator decides continuation from credit; add
> no stopping budget.

followed by "Resource instructions supplied from the frozen library:" and the sections the launch-instruction library
selects for the assigned resource (`for_resource`).

## Task and instructions

`instructions.py` composes the model instructions:
1. the goal text above *replaces* the default prompt (`replaces_default_instructions = True`; for a job source the
   job episode's instructions would be the base);
2. `REASONING_COMMIT_REQUIREMENT` only if `reason` is permitted (it is not: only `tool`);
3. tool-knowledge and launch-instruction-library instructions when those inputs are present;
4. the fixed `pending_child_delivery` → `redeliver_report` repair paragraph;
5. the in-process wait and native-event paragraphs only when `wait` is permitted (it is not);
6. under `decision_exchange_v1`, the request_context / `episode.history view=records` history paragraph.

`task.py`, `task_state.py`, `task_decision.py`, `task_action.py`, `decision_context.py`, `decision_exchange.py`,
`decision_contracts.py`, `decision_provider.py`, `report_delivery.py`, `waiting.py` are per-episode copies of the
old runner's task loop; their only own values are the class names and the grain / planning role `launch_local`.

## What it reads from its parent's assignment

Parent role must be `launch` (the `execution_job_submission` episode). The assignment is one request for a bound
resource whose kind is `local`: `anyOf` over `_request_schema(resource_id)` = the practical `ASSIGNMENT_SCHEMA`
with `resource_id` and `resource_kind` consts and `requested_job` alternatives (generic job, the seven native
BLAST / HMMER job kinds, preparation jobs), `workspace` confined to the resource workspace. `prepare_assignment`
also re-validates the parent's own `execution_launch_assignment_v1` (requests per resource, immutable input versions,
constraints, launch_instructions), masking / BLAST-utility job inputs, immutable input versions and native / standard
BLAST database job inputs. At execution time `_check_parent_inputs` re-reads the parent Launch request.
`required_return_sources` is empty.

`present_execution_context` (selected-execution prompt).

## Tools

One: `exec_command` {cmd (string or argv), workdir, target `resource`|`coordinator`, env} — "Execute the shell
command you write on the assigned resource ... Returns its actual output and saved action receipt." Each call opens
an idempotent intent per operation key, runs through `TerminalExecution`, finalizes the scientific command,
updates cwd / environment revision, assesses the assignment's validations and saves a receipt; failures are
receipts, not exceptions.

## Credit

`operational`. `credit_view` = the terminal service's `PracticalState.credit_view()` (in the old shared tree), or,
after closure, the frozen closed snapshot `execution_closed_operational_credit_v1` (`closed_credit.py`), which is
never reprojected. `handoff_unit` and `acquired_record_unit` are explicit positive configuration operands.

## Continuation

`yield_estimator.py`: requires `require_private_yield=True`; profile `task_yield_profiles['launch_local:' +
_request_yield_class(request)]` = `{cutoff, parameters}` (class e.g. `practical_local_native_blast_outputs`,
`practical_local_handoff`); `YieldController(epoch, initial_credit, cutoff, YieldParameters(**parameters),
estimate_with_context=PracticalYieldEstimator(verify_completion))`. The practical estimator gives an exact-zero
next gain once the assignment endpoint is verified. New-runner equivalent: **completion with a target**
(target = the assignment's verified endpoint), settings = that profile's cutoff and parameters.

## What it reports to its parent

Facts (`report_fields.py` / `native_return.py` / `to_parent.py`): `practical_completed`, `practical_receipt_digests`,
`practical_receipt_refs` (namespace `practical_receipt`), `execution_handoff_refs` (returnable handoffs read from its
own receipts), `execution_result_refs`, `execution_file_source_refs`, `execution_file_capture_outcomes`,
`execution_result_origin`, `execution_completed`, empty lists for every native result family, AppService support
refs when bound, and the closed credit fact. Every `x-source` field in the parent's form must equal the recorded fact.

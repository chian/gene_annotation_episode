## What this episode is for

Be the execution agent for one assigned job on the local resource (role `launch_local`, resource kind `local`), writing and running the shell code the job needs. In its own words (native_goal.py; the text is word-for-word the same as hpc_job_execution's):

> You are the execution agent for the actual job and resource assigned below. Use exec_command to write and run the shell code needed for that job. Choose scripts, environment preparation, software invocation and recovery from the actual resource instructions and observed results. No sequence of setup or job-stage operations is prescribed. Preserve the caller's scientific inputs, desired outputs and acceptance criteria. Historical inventory is context, not proof of present usability. Each command is one ordinary episode action: its actual result and earned credit enter the iterator, including failure or zero progress. Host bookkeeping records command versions and actual native job identities; do not maintain a parallel receipt ledger. If a submission outcome is uncertain, investigate that original submission rather than create a duplicate. Use the provided resource-specific instructions, account, storage and existing authentication route. workdir and env apply to the selected command only. target=resource runs on the assigned resource; target=coordinator runs in the local run directory for supplied-input and transport work. Both are ordinary journaled actions; resource computation belongs on its actual allocation. For coordinator-side transfers, execution_resource.ssh_argv, when present, is the exact configured transport prefix. Append the remote shell command as its final argument and preserve stdin. The supplied configuration gives the existing connection details. target=resource uses that transport directly. The episode iterator decides continuation from credit; add no stopping budget.

## Task and instructions

- Task statement above plus the frozen launch-library sections for this resource (`launch_instructions.for_resource`, reached through `services.workflow`).
- `goal.py` delegates `instructions` to the practical executor (`TerminalExecutionBehavior`).
- instructions.py is the composer (same text as hpc/api): specialist replaces default, then tool knowledge, launch library, child-delivery repair, wait/native-event guidance (inactive: `tool` only), exchange history text.
- Selected-task view (internal_summary.py `_with_selected_execution_task`, same construction as api goal.py): `selected_execution_task_v1` with parent `scientific_question` and `selected_tool_info` (`services.scientific_parent_task`), the request with resource kind, endpoint, constraints, the one chosen native job of the seven A104 kinds (HMMER jobs through `native_profile_scientific_job_view`), resource information, selector, result description.

## What it reads from its parent's assignment

- Parent must be `launch` of execution_job_submission.
- `practical_assignment_v1` with `resource_id`, `resource_kind` = `local`, confined `workspace`, `endpoint` (`usable_handoff`/`completed_job_outputs`), `requested_job`, `initial_context`.
- `child_assignment_schema` is the plain assignment schema (no frozen-request restriction, unlike hpc).
- `_check_parent_inputs`: original launch request, masking/utility inputs, pinned input versions, native/standard BLAST database job inputs. `initial_references` for `launch_local` collects masking/utility input refs from the single assignment.

## Children

None.

## Decision state and what the model sees

Generic decision context (same as siblings) plus `execution_assignment`, `execution_resource` (workspace, kind, policy, account, ssh_argv, python_executable, scheduler, inventory snapshot), `coordinator_workspace`, `execution_progress`, `execution_completion`, initial `execution_resource_information`, and the `selected_execution_task` view. Renderer `present_execution_context` (selected-execution renderer applies when that view is present).

## Tools it offers

One tool, `exec_command` (`cmd`, `workdir`, `env`, `target` resource|coordinator), with the same receipt handling as hpc: idempotent PracticalState begin/finish per operation key, `finalize_scientific_command`, cwd/env revision tracking, `assess_validations`, published `PracticalReceiptInformation` receipt; failure is a recorded completed action. Common actions: `tool` only.

## How credit is counted

`credit_kind = 'operational'`; live credit = `PracticalState.credit_view()` (old shared-root practical_execution_state, not read); frozen closed-credit view after closure. Not bounded.

## Continuation

Private yield binding required; profile `launch_local:<request class>` (`practical_local_<native jobs>_<handoff|outputs>`) from `task_yield_profiles` `{cutoff, parameters}`; `PracticalYieldEstimator(verify_completion)` = completion with a target. New layout: completion-with-target estimator with these settings.

## What it reports to its parent

Same facts as hpc: `practical_completed`, `practical_receipt_digests`, `practical_receipt_refs`, `execution_handoff_refs` (received plus returnable practical receipts), `execution_result_refs`, `execution_completed`, empty native families, AppService support refs when bound, closed-credit facts; `validate_report` requires recorded-fact agreement.

## Differences from siblings

- Versus hpc: role/resource kind, no frozen-request `enum`, and it adds the `selected_execution_task_v1` view to its decision context. All other files differ only in class names and module paths (60 of 62 files).
- Versus api: practical executor instead of service executor; no `wait`; task statement in native_goal.py.

## What this episode is for

Carry out one assigned job through a remote web service (role `launch_api`) and establish a usable monitoring/results handoff for it. In its own words (instructions.py):

> Carry out the assigned work through {service} using one selected operation each turn. Keep the original inputs, request, resource and parent constraints fixed. Choose useful preparation, service requests, observations or repair from the actual available operations and received outcomes. Distinguish an immediate returned response from a service job that continues remotely. Preserve the actual request or job identity and submission uncertainty; a missing reply does not establish that no job was created. Establish the requested usable monitoring/results handoff from recorded service facts. The configured controller governs continuation; verified original handoff completion gives exact zero future credit.

Services it can drive (api_service.py, hmmer_service.py, appservice_*.py): any `api` resource built by `build_service` (NCBI BLAST, UniProt, BV-BRC data, BV-BRC AppService), plus the legacy EBI HMMER `hmmer_api` resource (assignment version `api_execution_assignment_v1`).

## Task and instructions

- Instruction text: `APIInstructions.instructions` (above) with `{service}` from the validated assignment. `replaces_default_instructions = True`, so the specialist text replaces the runner default.
- task_instructions.py composes: specialist text + reasoning-commit requirement (if `reason` permitted; it is not) + tool knowledge + launch instruction library + pending child delivery repair text + wait guidance (when `wait` permitted) + native event guidance + exchange-protocol history text.
- Selected-task view (goal.py `_with_selected_execution_task`): `selected_execution_task_v1` = parent's `scientific_question` and `selected_tool_info` (from `services.scientific_parent_task`), the request(s) with resource kind, endpoint, constraints, job (EBI HMMER request as-is; native jobs restricted to the seven A104 kinds `native_blast`, `native_blast_masking`, `native_blast_utility`, `native_blast_database`, `native_blast_standard_database`, `native_hmmer`, `native_hmmer_preparation`, HMMER jobs through `native_profile_scientific_job_view`), resource information, selector and result description.

## What it reads from its parent's assignment

- Parent must be the `launch` role of execution_job_submission (`resource_child_role_owned_by_launch`).
- The assignment is one per-resource request validated by the API service (`validate_assignment` with scope) and by `_request_schema` (resource_id const; kind must be `api`).
- `_check_parent_inputs` re-reads the original Launch request from `runtime_episodes` and checks: the BLAST API parent request, masking and BLAST-utility inputs, pinned `immutable_input_versions`, native and standard BLAST database job inputs.
- Launch constraints honoured: `allowed_resource_ids`, `allowed_kinds`, `resource_id`, `kind`.
- `initial_references`: masking and utility input references.

## Tools it offers

The API service's `launch_catalog(request)` for the assigned resource (operation names come from the service). Legacy EBI HMMER: `api.hmmer.prepare`, `api.hmmer.databases`, `api.hmmer.submit`, `api.hmmer.status`, `api.hmmer.check_handoff`. Common actions: `tool`, plus `wait` when the assignment version is `api_service_assignment_v1`.

Rules carried in the service code: one operation key = one immutable intent; a reused key for different work is invalid; only one original remote-mutating submission (a retry only if the earlier one was `not_sent`); an unknown reply after restart is reported as unknown (`api_operation_response_unknown`), never as absence; `handoff_ready` publishes an `api_service_receipt_v1` handoff source.

## How credit is counted

`credit_kind = 'operational'`. Live credit (api_service.py / hmmer_service.py `credit_view`):

`credit = handoff_unit * (new distinct (resource_id, execution_id) handoffs not among initial refs) + acquired_record_unit * (new distinct result identities not among initial refs)`

Only references in the receiver's `known_record_refs` count; initial refs must be a subset of known. Binding records `scientific_credit: False`, `monitoring_credit: False`. Credit is finite, not bounded. After closure the credit view is frozen (closed_credit.py) and only that original view is returned.

## Continuation

`yield_controller` requires `require_private_yield`. Profile key `launch_api:<request class>` where the class is `api_<service>[_<algorithm>][_<database>]_handoff` (or `practical_<kind>_<native jobs>_<handoff|outputs>`); profile = `{cutoff, parameters}` from `task_yield_profiles`. Estimator: `PracticalYieldEstimator(verify_completion)`, i.e. completion with a target; a verified `practical_completion_v1` proof (endpoint `usable_handoff`, or `completed_job_outputs` for an AppService bundle whose requested form is satisfied) gives exact zero expected next gain. In the new layout this is the completion-with-target estimator in yield_control/ with the per-request-class `cutoff` and `parameters` as its settings.

## What it reports to its parent

Fact sources (report_fields.py) include `execution_handoff_refs`, `execution_result_refs`, `execution_completed`, `execution_result_origin` (None here), `execution_blast_hsps`, BV-BRC data / AppService (`bvbrc_appservice_support_refs`, homology, phylogeny, proteome) / UniProt facts, empty native family sources, and the BLAST graded return for results. The report form is the parent's typed form filled from saved interpretations plus recorded facts (report_delivery.py `form_with_facts`); `validate_report` rejects any `x-source` field that disagrees with recorded facts.

## Differences from siblings

- Only sibling with a remote-service executor (api_service.py, hmmer_service.py, appservice_*.py) and with `wait` permitted (for `api_service_assignment_v1`).
- Has `task_instructions.py` where hpc/local have `instructions.py` (same composer text).
- Its own `instructions.py` is the API task statement; hpc/local carry their task statement in `native_goal.py`.
- `_check_parent_inputs` also validates the BLAST API parent request (`_validate_blast_api_parent_request`, defined outside this folder).
- `goal.py` builds the selected-execution-task view (local does this in internal_summary.py; hpc does not).
- Its configuration builds `APIJobService` (own file); hpc/local build `APIRecordAccess` from the old shared library.

## What it is for (its goal, in its own words)

`goal.py` (one paragraph, quoted in full order, lightly abridged only where marked):

> Iterate toward the original accomplishment while balancing expected credit against real elapsed time and resource
> demand. The hpc parent can commission hpc_prediction and hpc_execution as sisters: prediction fits/measures/compares;
> execution prepares, launches, monitors and parses the selected work. Both assignments copy hpc_child_commission
> exactly and carry the hpc parent owner_episode_id. Both sisters inherit exactly hpc_child_scope, including an empty
> subject_refs list for an operational task with no biological inputs. Candidate IDs, model IDs, queue observations
> and resource IDs are not biological subject_refs. Use hpc_report_form as the return contract. Use the shared
> current model and comparisons; resource observations and candidate requests are different quantities. If suitable
> history is available, a prediction iteration can improve sizing before launching. No historical validation support
> means no invented model-improvement credit. Queue/setup costs belong to an allocation, which should carry enough
> useful work. When candidates are absent, discover the remote environment and documentation with hpc.discovery.run,
> then design candidate portfolios with hpc.candidate.propose. [...] Every work unit writes result.json and
> progress.json under os.environ["HPC_UNIT_DIRECTORY"] [...] Compute commands must run on allocated compute nodes
> using the facility launcher. Commission hpc_prediction only when model improvement warrants its own iteration.
> Compare portfolios using current queue features and measured history. A plan freezes its original forecast,
> scientific manifest and acceptance criteria. Commission launch -> launch_hpc with that actual job and resource.
> [...] Use hpc_launch_report_form as the Launch return contract. If a completed Launch return omitted its receipt,
> use redeliver_report with the existing delivery_ref and hpc_launch_report_form; report repair must not commission
> another Launch. Attach that received handoff. Use hpc.monitor once when another observation can affect your
> decision [...] Use hpc.results directly for known parsing. Commission monitor/results children only for actual
> investigation. [...] When pending_action is collect, use hpc.results for those original outputs; completion is not
> acceptance. When hpc_monitor_controllers is present, select hpc.monitor.wait for a scheduled observation [...]
> This preserves pending accomplishment value across waits without credit for sleeping. [...] Do not poll for credit
> or duplicate a submitted attempt. Never replace an uncertain submission. Accepted accomplishment, model improvement,
> and fixed prospective forecast validation are the only parent credit components; launch-local credits are not
> added again.

## Task and instructions

`task_instructions.py`: goal (replaces the default prompt) + tool knowledge + launch library + `pending_child_delivery`
repair paragraph + in-process wait paragraph and native-event paragraph when `wait` is permitted. No fixed
boundary / report / history blocks (the progress monitor has them). Task-loop files are old-runner copies with grain
/ planning role `hpc`; `decision_inputs.py` adds `requested_action_history` for HPC contexts.

## What it reads from its parent's assignment

`commission_id` (enum of configured commissions) or `commission_source_ref` (a reference the parent actually
received; read through `hpc_commission_sources`), and optionally `tool_request` `{name, resources, arguments_json,
result_reader, objective}`, resolved against the parent's real frozen tool library (`evolutionary_history_evidence_binding`)
into `{objective, tool_contract, arguments, result_reader, result_reader_options, execution_rule}` with the rule
"Implement this exact requested computation through the HPC template ... do not replace scientific grading with the
allocation acceptance score." With `require_commission_yield` the commission must carry `yield_bindings`.

## Credit

`operational`; `credit_view` = `HPCLedger.credit_view()` (contributions: accepted actual obligations, model
improvement, fixed prospective forecast validation; launch-local credits not added again).

## Continuation

`yield_controller`: `commission['yield_bindings'][role]` `{cutoff, parameters}`, estimator
`HPCContinuationEstimator(verify).with_continuation_cost(cutoff)` from the old shared library. For waits,
`continuation_for_action` writes a ledger continuation packet: remaining obligations; per plan a valuation from
`choose_schedule(conditional prediction, candidate, commission, policy, credited, now=time.time())` or, when outputs
await collection, the unresolved-acceptance upper bound and `pending_action='collect'`; pending credit deduplicated by
obligation; `active_credit_ceiling = 0` when every remaining obligation is pending and no new training cases exist;
active (non-passive) history indices; `earned_wait_credit = 0`. New runner: **completion with a target** (target =
the commission's obligations), settings = the commission's `yield_bindings['hpc']`.

## What it reports to its parent

`hpc_credit` (signed measured credit; repeated polling adds none), `hpc_model_ref` (namespace `hpc_model`; a closed
episode's model ref is checked read-only against its ledger), `hpc_accepted_obligations`, `hpc_result_refs`.
Recorded `x-source` fields must equal the evidence.

## Differences from similar episodes

- Shares the task-file family with `execution_progress_assessment` but drops the annotation-axis branch and fixed
  guidance blocks, adds `requested_action_history`, and has five child roles.
- `create_execution_bindings` builds its own five execution child bindings from its own child folders (its children
  are separate copies of the sibling execution episodes).

## Notes for the port

- `resource_discovery.py` runs `subprocess.run([...ssh_argv, command], timeout=90)`: an elapsed-time cutoff, which
  AGENTS.md forbids; it also hard-codes `cd /lus/flare/projects/BioReason-Aurora-Test`.
- `yield_estimator.py` scales schedule values with `min(1.0, expected/total)` (a forecast scale, not a credit bound).
- `resource_discovery.py` keeps at most 64 KiB stdout and 8 KiB stderr; `allocation_observations.py` refuses a window larger than the requested limit.

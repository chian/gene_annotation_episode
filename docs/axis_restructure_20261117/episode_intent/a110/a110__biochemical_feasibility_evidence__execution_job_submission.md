## Purpose (own words)

The A110 launch episode (role `launch`): choose which permitted concrete execution request to commission on which configured resource, and receive that resource child's usable handoff. `goal.py`:

> "Choose which permitted concrete execution request to commission on an explicit resource_id. Capabilities, recorded inventory and timing information inform the choice. Preserve the original job, immutable inputs, constraints and pinned instructions. A resource child owns iterative execution in the shared loop. Receive its requested typed handoff; no infrastructure chooses an approach. Actual received usable handoff completes this launch endpoint with exact zero future credit."

`replaces_default_instructions = True`, so this text replaces the default instructions.

## Task and instructions

- `task_instructions.instructions` carries this episode's own copy of the default `INSTRUCTIONS` ("You own an iterative scientific annotation improvement, not a tool itinerary ..."), `REASONING_COMMIT_REQUIREMENT` and `DECISION_EXCHANGE_PROTOCOL = 'decision_exchange_v1'`, then composes exactly as the head: specialist text replaces the default; reasoning requirement when reason is permitted; tool knowledge; launch library; pending-child redelivery; pending-child wait; native-event targets; decision-exchange history replacement.
- `task.py` / `task_decision.py`: the shared-shape decision loop; decision state from `decision_state`, report validation with grain `launch`, execution expectations captured for `launch`, waiting support when wait is permitted; no execution-context guard (unlike the head).
- `presentation.present_context`: same renderer precedence as the head (HPC, published-scientific, selected-execution, monitor, receiver).

## What it reads from its parent's assignment

`from_parent.assignment_schema`: `execution_launch_assignment_v1` = {`version`, `requests` (object keyed by configured resource id, minProperties 1; each a concrete practical assignment with `resource_id`/`resource_kind` consts and a `requested_job` that is the generic schema or, for resources with `native_flux_balance`, an FBA requested job pinned to the configured operation/mode/software/model formats), `immutable_input_versions` [INPUT_VERSION_SCHEMA], `constraints` (object), `launch_instructions` (selection schema)}; with any FBA resource configured the schema is `anyOf` [that, compact FBA launch]. `prepare_assignment`: validated with internal schemas; an `hpc`/`hpc_execution` parent's launch is authenticated (`hpc_work_planning.to_child_execution_job_submission.authenticate_launch`); a compact FBA launch is previewed through the request bindings; otherwise each request is validated, FBA inputs and immutable input versions checked against the parent and scope. `_permitted(assignment, resource_id)`: the resource is in `requests` and satisfies `allowed_resource_ids`, `allowed_kinds`, `resource_id`, `kind` constraints.

## Decision state and what the model sees

`internal_summary.decision_context`: `execution_assignment` (the launch assignment) and `execution_progress` (= this episode's own facts), plus `selected_execution_task` when every request carries `native_flux_balance` and the scientific parent task is available (scientific question, selected tool info, per-request resource id/kind/endpoint/constraints/FBA job view/resource information, selector, result description). For a compact FBA assignment: `practical_assignment`, `practical_progress` {credit, satisfied_keys}, `practical_completed`. `decision_state` is the common decision state (as in the head, without `investigation_progress`).

## Tools offered

`work_operations.catalog` = `launch_operation_catalog()` = only `execution.capabilities` ("Read the actual caller-bound resource configuration and already recorded inventory; no discovery or selection."). `execute` returns capability information or an invalid outcome (retained-artifact file-capture errors re-raised). `resource_information.resource_tool_contracts` (used by others) builds per-kind launch and results operation contracts with commission routes to `launch_local`/`launch_hpc`/`results`, plus native FBA tool contracts (skipping `perform_flux_balance_analysis` when the tool registry already has it as a direct tool). Permitted actions: tool, reason, child, wait, redeliver_report; under an `hpc` ancestor only tool, child, redeliver_report.

## Credit

`credit_kind` = `operational`. `project_credit`: a closed episode returns only its recorded closed view (authenticated against runtime episode completion, archive, observation history, receipt prefix and binding/context digests, `execution_closed_operational_credit_v1`); otherwise live credit = `handoff_unit` × (resource ids with a usable handoff received, not already in the initial handoffs) + `acquired_record_unit` × acquired fraction (fixed 0.0 here), with `operational_credit_binding` {`execution_received_records_credit_v1`, units, qualification}. Units are positive finite configuration operands; nothing bounds or rescales credit.

## Continuation

Yield estimator: bounded quality. Requires `require_private_yield`. Remaining = (eligible original requests not already handed off at entry) × `handoff_unit`; profile `task_yield_profiles['launch:' + '+'.join(sorted request classes)]` ({cutoff > 0, parameters}); request class = `practical_<kind>_<native_*...>_<handoff|outputs>` or `compact_<version>` → `BoundedYieldController(epoch, initial_credit, cutoff, remaining, YieldParameters(...))`. When nothing remains (initial credit must be 0) an exact-zero forecast `launch_original_request_exhaustion_v1` with cutoff 0 (any non-zero later credit raises). `practical_estimator` = `PracticalYieldEstimator(verify_completion)`. Completion: an action is complete when its record refs include a usable handoff for this assignment (`practical_completion_v1`, endpoint `usable_handoff`).

## Report to parent

`to_parent.facts`: FBA fact sources (empty lists when FBA results are configured), `execution_handoff_refs`, `execution_result_refs` (result bodies with windows), `execution_file_source_refs`, `execution_file_capture_outcomes`, `execution_result_origin` (NATIVE_RESULT_ORIGIN when windows exist), `execution_completed`, plus the closed operational-credit snapshot. `validate_report`: FBA returns validated; references resolve; each fact field must equal the recorded fact. `context_receipts.required_return_sources`: `execution_handoff_refs` when the parent is the A110 head and an annotation task is required. `report_delivery.finish` as in the head.

## Differences from similar episodes

- Compared with A107's `execution_job_submission`: A110 has no `api_job_execution` child (only local and hpc), no API request classes in `_request_yield_class`, and configures native **flux-balance** (FBA) resources (`native_flux_balance`, local only) instead of A107's BLAST/HMMER/Infernal/expression-NMF/RNA-structure resource bindings and result-reader installation.
- Compared with its children: it owns no resource state (`state` raises `practical_resource_role_required`), its credit counts handoffs rather than practical receipts, and its yield is bounded by the original request map.

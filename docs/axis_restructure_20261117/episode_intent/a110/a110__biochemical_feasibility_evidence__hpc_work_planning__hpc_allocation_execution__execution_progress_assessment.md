# a110 / biochemical_feasibility_evidence / hpc_work_planning / hpc_allocation_execution / execution_progress_assessment

Source: `git show 97308b94c:gene_annotation_episode/episodic_workflow/root/a110/biochemical_feasibility_evidence/hpc_work_planning/hpc_allocation_execution/execution_progress_assessment/<file>`. Only this folder and its `tests/` were read. Old binding classes: `MonitorEpisode` (binding) and `ProgressMonitoringTask` (decision source). Old role name: `monitor`.

## What it is for (its own words)

`goal.py`: "Investigate which further exposed progress information is useful for the assigned target. Use actual status, measured quantities, committed references and source-bound logs. Liveness establishes process presence only; elapsed time alone establishes neither productive work nor a stall. Unknown information stays unknown. Earlier outcomes and your admitted child forms inform later decisions. You may explicitly commission an ordinary monitor for one exposed direct dependency; no descendant traversal, fanout, cadence or depth is prescribed. Return the original parent's typed form at your closure even while the target remains active. Do not report private reasoning, intentions or unrestricted findings. Recorded facts use saved delivered observations; closure does not poll or compose another report with a model." Then either "The monitor's information-credit projector and bound yield rule govern continuation." (private yield configured) or "The caller's monitoring projector and configured controller own credit and continuation.", then "Repeated observation identities and read timestamps alone earn no new information."

Planning context (`goal.py`): objective = the parent's goal; unresolved question "Which exposed progress information would improve the original requested report?"; progress definition "Actual received information under the caller-bound monitoring projector; repeated identities and timestamps alone earn no credit."

## Task and instructions

The model instructions (`task_instructions.py`) are the goal text above followed by this episode's own guidance blocks: ACTION_BOUNDARY (do not emit a stop action or invent a turn budget, approval review, quality gate, experiment, term or observation), CREDIT_COMPONENT_GUIDANCE (current_evidence_vector is a progress proxy, not biological truth), RESOURCE_ESTIMATE_GUIDANCE (a timing experiment earns monitoring credit for timing information learned; job elapsed time and own monitoring action duration are distinct), REPORT_GUIDANCE (child returns only the parent's typed form; report_update is the interpretation before the next action; redeliver_report repairs representation only), HISTORY_GUIDANCE or EXCHANGE_HISTORY_GUIDANCE, HOST_EXECUTION_GUIDANCE, then tool-knowledge and launch-instruction text when present, REPAIR_GUIDANCE, and when wait is permitted WAIT_GUIDANCE (wait on a pending_child_ handle with event returned, after_cursor 0) and NATIVE_EVENT_GUIDANCE. Of the four episodes here, only this one has its own monitor-specific instruction blocks; the others use the shared default text or only their binding text.

## What it reads from its parent's assignment

`monitor_assignment_v1` (`contracts.py`, `from_parent.py`): `target_handle` (must be in scope as an `execution_handle`), `requested_fields` (subset of execution_status, measurements, log_windows, committed_record_refs, dependencies, result_available), `known_progress_refs` (each must be a snapshot of the same target), `permitted_committed_record_types` (record types it may report). The parent's goal and report contract (requested form, initial report values) arrive with the request.

## Children it may commission

One slot: itself (`monitor`, recursive), offered only when the target exposes direct dependencies (`allowed_children`).
- Sends (`to_child_execution_progress_assessment.py`, `from_parent.prepare_assignment`): a `monitor_assignment_v1` whose `target_handle` is one exposed direct dependency of the parent's target and whose `permitted_committed_record_types` is a subset of the parent's.
- Takes back (`from_child_execution_progress_assessment.py`): the child's typed form; every `episode_progress` reference in it is read and recorded as received progress for this episode under the delivery operation key (with a digest of form, schema and scope), so it becomes part of this episode's received information.

## Decision state shown to the model

Common state (`decision_state.py`): goal, scope, working state, visible record refs, current credit and evidence vector, investigation progress (when receipts project it), credit binding, time accounting, pending work, last local outcome and feedback, visual evidence, report deliveries, controller state and binding, tools, tool knowledge, job episode options, available report facts, requested report purpose and form, current report update and basis, report lifecycle note; plus `monitoring_information_credit` and `monitoring_information_binding` when the credit view has them. Decision inputs (`decision_inputs.py`): resource context, launch instruction library and selected launch instructions, child options, completed action reports, pending work, execution expectations for `monitor`, resource tool estimates and native execution expectations, waiting support, contract-information profile.
Its own part (`internal_summary.py`): `monitor_assignment`, `monitor_target_description`, `monitor_direct_dependencies`, `monitor_received_progress_refs`, `monitor_information_meaning` ("Exposed direct relationships and already delivered observations. Empty measurements/log windows do not assert absence or a stall.") and `monitor_goal` (the planning context).

## Tools

`progress_operations.py`: `progress.observe` (selected fields of the assigned target, never wider than `requested_fields`; optional `native_operation` when the target descriptor supplies a selected observation schema; retains the observation identity when facts are unchanged; never traverses dependent work), `progress.read` (an already received observation), `progress.log` (one retained log window of a received observation, the window's artifact must be one of the source's representations; read through `source.read` with exact byte offsets). Permitted actions: tool, child, wait, redeliver_report. Invalid tool use returns an `invalid` outcome with feedback code (it still enters the iterator).

## Credit

Kind `monitoring`. Credit view is the caller-bound projector (`services.bound_role_credit`). `credit.information_credit()` selects `ProgressInformationCredit(progress_reader, information_unit)`: newly informative received snapshot count times information_unit (per the yield estimator's binding text `newly_informative_received_snapshot_count_times_information_unit`). Repeated identities and timestamps earn nothing. Credit is never bounded in these files.

## Continuation

Old: `yield_estimator.py` `_monitor_information_yield`: credit must not decrease (raises otherwise), `estimate_nonnegative_yield`, estimator binding `monitor_information_accumulation_v1`, forecast "next monitor action information credit", decision "predicted upper gain at or below monitor cutoff"; `YieldController(epoch, initial_credit, cutoff, YieldParameters(uncertainty_alpha))`. Only when private yield settings `{kind: information_accumulation, cutoff, uncertainty_alpha}` were configured; otherwise the caller's controller decides. New estimator: accumulation (settings: cutoff, uncertainty_alpha, information_unit).

## What it reports to its parent

Fact sources (`to_parent.py`): `monitoring_progress_refs`, `monitoring_target_handle`, `monitoring_execution_state` (latest delivered target observation; null when none), `monitoring_result_available`, `monitoring_observed_at_unix_seconds` (UTC, not refreshed), `monitoring_committed_record_refs` (only parent-permitted record types), `monitoring_dependency_handles` (direct only). Facts are built only from delivered observations; report construction never polls. `validate_report` requires every x-source field to equal its fact and every reported record reference to be permitted and received. `monitoring_progress_refs` is a required return source when the parent is `biochemical_feasibility_evidence` and an annotation task is required. Without a report contract, the finish record is credit, pending handles and current report facts.

## Differences from similar episodes

- Only episode of the four that commissions itself recursively and permits `wait`.
- Same file set (minus `contracts.py`, `progress_*`, `received_progress.py`) as other axes' execution_progress_assessment homes; its task files differ from `hpc_resource_prediction` by delivery_ref handling, wait execution, redelivery and child options.
- Its `task_instructions.py` carries monitor-specific guidance text that the result-acquisition and literature episodes do not have.

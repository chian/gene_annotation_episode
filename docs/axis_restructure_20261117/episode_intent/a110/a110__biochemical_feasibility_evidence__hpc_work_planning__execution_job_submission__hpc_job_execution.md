## What this episode is for

It is the execution agent for one actual job on one configured HPC resource (kind `pbs_ssh`). In its own words (`terminal_execution.py`):

> You are the execution agent for the actual job and resource assigned below. Use exec_command to write and run the shell code needed for that job. Choose scripts, environment preparation, software invocation and recovery from the actual resource instructions and observed results. No sequence of setup or job-stage operations is prescribed. Preserve the caller's scientific inputs, desired outputs and acceptance criteria. Historical inventory is context, not proof of present usability. Each command is one ordinary episode action: its actual result and earned credit enter the iterator, including failure or zero progress. Host bookkeeping records command versions and actual native job identities; do not maintain a parallel receipt ledger. If a submission outcome is uncertain, investigate that original submission rather than create a duplicate. Use the provided resource-specific instructions, account, storage and existing authentication route. workdir and env apply to the selected command only. target=resource runs on the assigned resource; target=coordinator runs in the local run directory for supplied-input and transport work. Both are ordinary journaled actions; resource computation belongs on its actual allocation. For coordinator-side transfers, execution_resource.ssh_argv, when present, is the exact configured transport prefix. Append the remote shell command as its final argument and preserve stdin. The supplied configuration gives the existing connection details. target=resource uses that transport directly. The episode iterator decides continuation from credit; add no stopping budget.

Then, when a launch instruction library is configured: "Resource instructions supplied from the frozen library:" followed by the sections selected for this resource.

The goal is a validated completion of the assignment's requested endpoint (`usable_handoff` or `completed_job_outputs`) with recorded command receipts.

## Task and instructions

- Role `launch_hpc`; commissioned by `biochemical_feasibility_evidence/hpc_work_planning/execution_job_submission` (as a child of its `launch` role). Entry roles: none.
- `replaces_default_instructions=True`: the instruction text above replaces the default runtime instructions. `task_instructions.py` then appends tool knowledge (when present), the launch instruction library text, the pending-child redelivery repair paragraph, and (for the exchange protocol) the request_context/episode.history guidance.
- Only common action: `tool`. No reason, child, wait or redeliver actions are permitted by the binding (the copied task loop still contains those branches).

## What it reads from its parent's assignment

A concrete practical assignment (`practical_assignment_v1`, from `practical_execution_records.ASSIGNMENT_SCHEMA`) for one configured resource: `resource_id` (const), `resource_kind` = `hpc` (const), `requested_job` (generic schema or native flux-balance alternatives per resource binding), `endpoint`, `workspace`, `initial_context`, constraints. Under a `launch` parent with an `hpc` ancestor the schema is an enum of the frozen hpc requests the launch assignment permits (allowed_resource_ids / allowed_kinds / resource_id / kind constraints). It checks that the parent is `launch`, that the resource kind matches, and that the launch's `immutable_input_versions` validate (including flux-balance inputs). At start (`science._check_parent_inputs`) it re-reads the launch parent's original request and re-validates those versions.

The prompt is rendered by `presentation.present_context` (hpc prompt for hpc contexts).

## Tools

`operation_catalog('hpc')` (old shared `library/execution_operation_information`; exec_command-style command execution with `target` resource/coordinator, `workdir`, `env`). Each command: arguments validated, `TerminalExecution.validate_action`, intent recorded, executed, `finalize_scientific_command`, validations assessed, receipt finished and published as a practical receipt record. `resource_information.resource_tool_contracts` also describes the launch and result operations per resource for the parent's commission routes.

## Credit

Kind `operational`. Live: the practical state's own credit view (`PracticalState.credit_view()`, defined in the old shared `practical_execution_state`, not in this folder; validation-predicate progress toward the requested endpoint). After closure: only the closed credit view saved in the final facts, authenticated against the yielded completion, archive, observation history and receipt prefix. Credit is a finite number; nothing bounds or rescales it.

## Continuation

Requires `require_private_yield=True`. Profile `task_yield_profiles['launch_hpc:<request class>']` = `{cutoff, parameters}`; request class `practical_hpc[_native_*]_{handoff|outputs}` (or `compact_<version>`). Old `YieldController(epoch, initial_credit, cutoff, YieldParameters(**parameters), estimate_with_context=PracticalYieldEstimator(verify_completion))`: an endpoint estimator that gives zero further gain once a recorded completion proof verifies. Maps to the new **completion with a target** estimator; settings are that cutoff and parameters per request class.

## Report to parent

Facts: `practical_completed`, `practical_receipt_digests`, `practical_receipt_refs`, `execution_handoff_refs`, `execution_result_refs`, `execution_file_source_refs`, `execution_file_capture_outcomes`, `execution_result_origin` (current-filesystem qualification), `execution_completed`, empty FBA fact sources when FBA is configured, and `execution_closed_operational_credit_v1` at closure. Report fields with `x-source` must equal the recorded facts. `required_return_sources` returns `()`.

## Differences from siblings

- Identical to `local_job_execution` except: role `launch_hpc` vs `launch_local`; the hpc `child_assignment_schema` restricts to frozen hpc launch requests; hpc has no compact flux-balance assignment path in `prepare_assignment`; `internal_summary` line 58 returns the context unchanged for non-compact assignments (local builds the request map); yield profile prefix `launch_hpc:`.
- Unlike `execution_result_acquisition` (role results, byte-coverage credit) it acquires nothing; it runs commands and reports receipts/handoffs.
- `execution_result_acquisition/yield_estimator.py` carries a copy of this episode's `_launch_hpc_yield_controller` (unused there).

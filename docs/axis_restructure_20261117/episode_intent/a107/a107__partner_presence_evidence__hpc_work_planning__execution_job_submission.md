# A107 `partner_presence_evidence/hpc_work_planning/execution_job_submission` (launch)

Source: `git show 97308b94c:gene_annotation_episode/episodic_workflow/root/a107/partner_presence_evidence/hpc_work_planning/execution_job_submission/<file>`. These are the episode's own 39 files directly in its folder. It has no `grading/` or `scoring/` folder. Its `tests/` folder and its three child folders were not read for this note.

Old internal names: the class is `ExecutionEpisode`, assembled from the mixins `Launch*`. The role is `launch`. The binding path is `partner_presence_evidence/hpc_work_planning/execution_job_submission`. The version is `execution_episode_v1`.

## Purpose (its own words)

`goal.py`:

> Choose which permitted concrete execution request to commission on an explicit resource_id. Capabilities, recorded inventory and timing information inform the choice. Preserve the original job, immutable inputs, constraints and pinned instructions. A resource child owns iterative execution in the shared loop. Receive its requested typed handoff; no infrastructure chooses an approach. Actual received usable handoff completes this launch endpoint with exact zero future credit.

This is the launch step under A107 HPC work planning. It receives a map of concrete execution requests, one per configured resource. It decides which resource child to commission for each request. It ends when every eligible request has a usable handoff (a job identity or result location that the results step can acquire).

## Task and instructions

- `replaces_default_instructions = True`: the goal text above replaces the default episode instructions.
- `task_instructions.py` then appends the following, each only when it applies:
  - the reasoning-commit requirement, if `reason` is permitted;
  - tool knowledge;
  - the launch instruction library text;
  - the pending-child redelivery repair text ("When pending_child_delivery is supplied ... select redeliver_report with a corrected form ...");
  - the in-process child wait text ("A pending_child_ handle names your original in-process child ... Waiting only reports readiness and earns no scientific credit"), if `wait` is permitted;
  - the native event targets text ("A target is registration metadata, not proof that submission succeeded ..."), if native event information exists and `wait` is permitted;
  - the decision-exchange history guidance, which replaces the fresh-conversation paragraph.
- Prompt rendering (`task_presentation.present_launch_context`) uses the first renderer that matches: HPC prompt, A107 head scientific prompt (`render_partner_presence_evidence_prompt`), API launch prompt, RNA comparison/structure results prompts, selected-execution prompt, monitor prompt, RNA comparison receiver prompt. If none matches, the context is passed as JSON.

## What it reads from its parent's assignment

`from_parent.assignment_schema` defines the assignment, version `execution_launch_assignment_v1`:

- `requests`: an object keyed by configured `resource_id`, with at least 1 property.
  - Each value is that resource's concrete request schema (`launch_request_schema`). For an API resource it is the service's assignment schema. Otherwise it is the practical `ASSIGNMENT_SCHEMA`, with `resource_kind` const and `requested_job` anyOf: the generic job, plus the resource's own native job alternatives (BLAST variants, HMMER, Infernal, RNA structure, expression NMF, preparation jobs).
  - The value can also be a BLAST graded request (`BLAST_GRADED_REQUEST_VERSION`), which must name an `ncbi_blast` resource.
- `immutable_input_versions`: an array of `INPUT_VERSION_SCHEMA`.
- `constraints`: optional `allowed_resource_ids`, `allowed_kinds`, `resource_id`, `kind`.
- `launch_instructions`: a selection from the launch instruction library.

`prepare_assignment` checks the following, in order:

1. If the commissioning parent role is `hpc`/`hpc_execution`, it authenticates the launch against `hpc_work_planning.to_child_execution_job_submission.authenticate_launch`.
2. It validates every request (`_validate_request`; API requests through `api_execution.validate_assignment`).
3. It validates the masking and utility inputs, the immutable input versions (including NMF), and the native BLAST-database, standard BLAST and RNA-structure job inputs.

`_permitted(assignment, resource_id)` holds when the request exists and the resource passes every constraint.

## Tools it offers

- Its own tool is `execution.capabilities` (`resource_information.launch_operation_catalog`): "Read the actual caller-bound resource configuration and already recorded inventory; no discovery or selection." The tool takes an empty input. It returns `execution_capability_information`, or an invalid outcome with the error code.
- `resource_tool_contracts` declares, for each configured resource, the launch and results operations with an `invocation_route` of kind `commission`: `entry_role` launch/results, the `resource_id`, and the `resource_role` launch_api/launch_local/launch_hpc/results. For API resources these are the service's own operation contracts plus homology API contracts. For local/HPC resources they are `operation_catalog(kind)` plus the native results catalog (`execution.results.status|collect|read`, byte window at most 1 MiB), plus the native NMF, RNA-structure, Infernal, Infernal-preparation and other native/preparation operation contracts.
- Actions: `tool`, `reason`, `child`, `wait`, `redeliver_report`. When any path ancestor role is `hpc`, the actions are only `tool`, `child`, `redeliver_report`.

## How its credit is counted

- Credit kind is `operational` (`credit_kind`).
- Live credit (`_live_project_credit`):
  - `credit = handoff_unit * new_handoff_count + acquired_record_unit * acquired_fraction`.
  - `new_handoff_count` is the number of distinct `resource_id`s with a received usable handoff, minus those whose handoff was already among the initial known refs.
  - `acquired_fraction` is fixed at `0.0` in this episode, so the acquired-record term is always zero here.
  - The view also reports `new_handoff_count`, `new_acquired_record_count`, and `operational_credit_binding` (`execution_received_records_credit_v1`, units, qualification `original_request_resource_scope_selector_and_actual_received_unique_information`).
- Closed credit: on closing, the projected view is captured in the facts under `execution_closed_operational_credit_v1`, together with context, binding, completion, archive, history and receipt-prefix digests. Afterwards `project_credit` returns that saved view unchanged. It is never re-projected. Credit is never bounded or rescaled; the units come from configuration.

## Continuation (yield estimator and settings)

`yield_estimator.ExecutionEpisodeYield._launch_yield_controller`. A private yield binding is required (`require_private_yield`).

- Eligible requests are those that are permitted. `remaining = (eligible resource_ids without an initial usable handoff) * handoff_unit`.
- If `remaining > 0`, it uses `BoundedYieldController(epoch, initial_credit, cutoff, remaining, YieldParameters(**parameters))`.
  - The profile comes from `task_yield_profiles['launch:' + '+'.join(sorted request classes)]`.
  - Request class: `practical_<resource_kind>_<sorted native_* keys>_<handoff|outputs>`, or `api_<service>[_<algorithm>][_<database>]_handoff`, or `compact_<version>`.
  - In the new layout this maps to the "completion with a target" estimator, where the target is the remaining uncredited request credit. The settings are `cutoff` and `parameters` per profile key.
- If `remaining == 0`, the initial credit must be 0, and it uses an exact-zero estimate (`launch_original_request_exhaustion_v1`).
- Completion (`completion.py`):
  - An own completed action that yields a usable handoff matching this assignment is the `usable_handoff` endpoint, with proof `practical_completion_v1`.
  - A verified proof gives exact zero next gain.
  - A closed episode reuses a verdict only if exactly one recorded observation carries it.

## Differences from siblings and similar episodes

- **A101 `sequence_homology_evidence/execution_job_submission`.** The goal text is identical, and both restrict actions under an `hpc` ancestor.
  - A101's launch also has BLAST custody, received-context and pending-work modules, which A107 lacks.
  - A107's launch is commissioned by `hpc_work_planning`, not by the axis head. It authenticates through `hpc_work_planning.to_child_execution_job_submission.authenticate_launch`; A101 uses its own `hpc_launch_authentication`.
- **Where the HPC request freeze lives.** In A101 the launch's own `child_assignment_schema` freezes a `launch_hpc` child's assignment to the permitted HPC requests. In A107 the launch's version of that branch is dead code (`and False`), and the freeze lives in the HPC child's `from_parent.py` instead.
- **HPC launch report contract.** A107's launch task also attaches `validate_hpc_launch_report_contract`.
- **Resource children.** Its three children are near-copies of one another. See their notes for the per-kind differences: the API child has its own goal text and a `wait` action; the HPC child freezes its assignment to the parent's HPC requests; only the HPC child omits the selected-execution-task view.
- **Old shared-root imports.** It imports many old shared-root modules: `root.a107.execution_contracts`, `a107_execution_bindings`, `a107_blast_execution`, `practical_execution_*`, `native_*`, `library/*` and others. Those are not to be restored. Their functions now live in `episode_support/` per the placement plans.

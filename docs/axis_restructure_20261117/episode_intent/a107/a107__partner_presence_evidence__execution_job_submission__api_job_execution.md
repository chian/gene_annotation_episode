## Purpose (own words)

`goal.py`: "Carry out the assigned work through {service} using one selected operation each turn. Keep the original inputs, request, resource and parent constraints fixed. Choose useful preparation, service requests, observations or repair from the actual available operations and received outcomes. Distinguish an immediate returned response from a service job that continues remotely. Preserve the actual request or job identity and submission uncertainty; a missing reply does not establish that no job was created. Establish the requested usable monitoring/results handoff from recorded service facts. The configured controller governs continuation; verified original handoff completion gives exact zero future credit."

## Task and instructions

`replaces_default_instructions = True`: the goal text is the specialist instruction. `task_instructions.py` adds the reasoning-commit requirement when reason is permitted (it is not: API allows tool, and wait for `api_service_assignment_v1`), tool knowledge, launch library instructions, pending-child-delivery repair, and — because wait is permitted for service assignments — the pending-child wait paragraph and the native-event-target wait paragraph; plus the exchange-protocol history replacement.

## What it reads from its parent's assignment

One concrete request for one API resource: the API service's own assignment schema (`api_execution.assignment_schema(resource_id)`) with `resource_id` const (`from_parent._request_schema`; schema is `anyOf` over API resources). `prepare_assignment` requires the parent role `launch`, validates through `api_execution.validate_assignment`, checks the resource kind, re-reads the parent's original launch assignment, applies `_validate_blast_launch_selection`, masking/utility inputs, input versions and native/standard BLAST and RNA inputs. `science._check_parent_inputs` repeats these against the parent row on initialize/execute and adds `_validate_blast_api_parent_request`: for a BLAST-graded parent request the selected service must be `ncbi_blast`, permitted, with the same query sequence digest and database.

## Continuation

`_launch_api_yield_controller`: profile `launch_api:<request yield class>` (e.g. `api_<service>[_<algorithm>][_<database>]_handoff`) from `task_yield_profiles` → `YieldController(epoch, initial_credit, cutoff, parameters, estimate_with_context=PracticalYieldEstimator(verify_completion))` — accumulation with a completion-aware estimator (verified original handoff completion forecasts exact zero). `verify_completion`: recorded closed verdict, else `api_execution.verify_completion`.

## Report to parent

`facts`: empty native fact families + `api_execution.facts(context, completion_snapshot)` + `execution_result_origin: None` + closed-credit facts. `validate_report`: native adapters, UniProt/Rfam hosts, reference resolution, `x-source` fields equal recorded facts.

## Differences from its sibling hpc_job_execution

- Goal text is its own API-service text; HPC's goal is the TerminalExecutionBehavior execution-agent text.
- Permits `wait` for service assignments; adds `waiting_support` and the wait/native-event instruction paragraphs (HPC has none).
- Has the BLAST-graded parent request check (`science._validate_blast_api_parent_request`, `prepare_assignment._validate_blast_launch_selection`).
- Credit/completion/facts go through `api_execution`; HPC goes through the practical delegate and its receipts.
- `internal_summary._with_selected_execution_task` (ebi_hmmer task view) exists only here.

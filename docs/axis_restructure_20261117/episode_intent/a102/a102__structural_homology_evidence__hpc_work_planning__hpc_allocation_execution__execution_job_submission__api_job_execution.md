Old identity: binding path `structural_homology_evidence/hpc_work_planning/hpc_allocation_execution/execution_job_submission/api_job_execution`, old role name `launch_api`, commissioned by `.../execution_job_submission` (old role `launch`). It was not an entry point (`entry_roles = ()`).

## What this episode is for

It carries out one assigned job through one configured API service and hands back a usable handoff for monitoring and results. Its goal, in its own words (`goal.py`; `{service}` is the assignment's `service`):

> Carry out the assigned work through {service} using one selected operation each turn. Keep the original inputs, request, resource and parent constraints fixed. Choose useful preparation, service requests, observations or repair from the actual available operations and received outcomes. Distinguish an immediate returned response from a service job that continues remotely. Preserve the actual request or job identity and submission uncertainty; a missing reply does not establish that no job was created. Establish the requested usable monitoring/results handoff from recorded service facts. The configured controller governs continuation; verified original handoff completion gives exact zero future credit.

## Task and instructions

One unit of its cycle is one selected action: a service operation (a tool), or a wait when the assignment is a service job that continues remotely. Each decision the model returns a `selection` and a `report_update` (its current interpretation for the parent's form). A selection that fails admission creates no unit: the model gets feedback and decides again. A failed model call ends the episode's source as `source_failed`. A selected operation that raises is recorded as a failed outcome and still enters the iterator with its credit.

Instructions are composed in `instructions.py` in this order:

1. the goal text above;
2. the shared reasoning-commit requirement, only if `reason` is a permitted action (it is not permitted here, see below);
3. tool-knowledge instructions and launch-instruction-library instructions when those inputs are present;
4. the `pending_child_delivery` repair paragraph (redeliver a finished child's report with a corrected form);
5. when `wait` is permitted, the paragraph on waiting for a `pending_child_` handle, and, when native event targets exist, the paragraph on `native_event_targets`;
6. under the exchange protocol, a paragraph telling the model to use `request_context` for its own attempt metadata and `episode.history` for exact earlier outcomes.

Permitted actions (`action_policy.py`): `tool`; plus `wait` only when the assignment's version is `api_service_assignment_v1`. No `reason`, no `child`.

The prompt is rendered by this episode's own renderer, `render_api_launch_prompt`, when the decision context is an API-launch context and neither an HPC nor a published-scientific context (`decision_provider.py`). The renderer itself is imported from outside the folder.

## What it reads from its parent's assignment

- Its own assignment: the request the parent selected for one configured API resource. The schema is the API service executor's assignment schema for that resource with `resource_id` fixed to it (`from_parent.py`, `parent_input_custody.py`). Fields this folder reads from it: `version` (`api_execution_assignment_v1` or `api_service_assignment_v1`), `service`, optional `algorithm` and `database`, `resource_id`. The full schema lives in the API service executor, outside this folder.
- From the parent's own launch assignment (`execution_launch_assignment_v1`): `requests` (per resource), `immutable_input_versions`, `constraints` (`allowed_resource_ids`, `allowed_kinds`, `resource_id`, `kind`) and `launch_instructions`. The old code re-read this from the parent's recorded request before initialising and before every operation, and re-validated the protein-structure job inputs and the immutable input versions each time.
- From the request message: `initial_report` (starting values of the report), `episode_assignment.launch_instructions` (selected launch instructions shown to the model), `job_assignment`, and the report contract (its schema and stated purpose).
- Admission rules: the parent must have role `launch`; the selected resource must be of kind `api`; the request must be valid for the API executor in the given scope.

## Children

None. `child_roles` and `allowed_children` both return nothing.

## Decision state and what it shows the model

State kept between decisions (`task_state.py`): the decision counter, `feedback` from the last rejected or failed step, the last outcome and its index, the current `report_values` (starting from the parent's `initial_report`) and the record refs they were based on.

Shown to the model at each decision:

- base state (`decision_state.py`): `goal`, `scope`, `working_state`, `visible_record_refs`, `current_credit`, `current_evidence_vector`, `credit_binding`, `time_accounting`, `pending_work`, `last_local_outcome`, `feedback`, `visual_evidence`, `report_deliveries`, `controller`, `controller_binding`, `tools`, `tool_knowledge`, `job_episode_options`, `available_report_facts`, `requested_report_purpose`, `requested_form`, `current_report_update`, `current_report_basis_refs`, `report_lifecycle`;
- this episode's own fields (`internal_summary.py`): `execution_assignment`, `execution_progress` (its current recorded facts), plus anything the API service executor adds;
- at the first decision (`resource_information.py`): `execution_resource_capabilities` (per resource: id, kind, availability `unknown`, tool names, workspace, policy, account, python executable, service, base URL, inventory snapshot, and for API resources `api_configuration_facts`) and `execution_initial_information`;
- extra inputs (`decision_inputs.py`): `resource_context`, `shared_information_context`, `launch_instruction_library`, `selected_launch_instructions`, `child_options`, `completed_action_reports`, `requested_action_history` (HPC contexts), `pending_work`, `execution_expectations` captured for `launch_api`, `resource_tool_estimates`, `native_execution_expectations`, `waiting_support` (when wait is permitted), `contract_information_profile`;
- under the exchange protocol, the per-action yield table, and the answers to its own lookups (child options, composition information, own earlier attempts).

## Tools it offers

The tool list is the API service executor's catalog for this assignment (`api_operations.py`). The entries are defined outside this folder. This folder's constants describe one launch operation, `execution.capabilities` ("Read the actual caller-bound resource configuration and already recorded inventory; no discovery or selection."). Every tool execution first re-checks the parent launch's inputs, then runs through the API service executor with the operation key `<run>:<episode>:<decision index>`.

## How its credit is counted

Credit kind is `operational` (`credit.py`). The live credit is the API service executor's credit view for this episode; the executor is built with two positive units from configuration, `handoff_unit` and `acquired_record_unit`. The formula itself is in the executor, outside this folder. After each tool action the task records the current credit view's `credit`; a wait keeps the last observed credit. Once the episode has closed, the view captured at closure is the only credit returned afterwards (`closed_credit.py`). Nothing in this folder bounds, clamps or rescales the credit.

## Continuation

`yield_estimator.py`. The episode must have its own yield enabled (`require_private_yield`), otherwise it raises. It picks the profile named `launch_api:<class>` from `task_yield_profiles`, where `<class>` is `api_<service>[_<algorithm>][_<database>]_handoff`; a missing profile raises `execution_original_task_yield_profile_required`. Each profile is `{cutoff > 0, parameters}`. The old controller was `YieldController(epoch, initial_credit, cutoff, YieldParameters(**parameters))` with `PracticalYieldEstimator(verify_completion)`: a completion proof that verifies gives exact zero expected future gain.

Of the three current estimators, the one with this end state is completion with a target. The old code has no numeric target: it has the proof check. The port has to state what the target is.

## What it reports to its parent

The parent's typed form, filled with recorded facts and the latest admitted interpretations (`report_delivery.py`). Facts a parent may request (`to_parent.py`): `execution_handoff_refs`, `execution_result_refs`, `execution_completed`, `execution_result_origin` (always null for this episode's live facts). The values come from the API service executor's facts. A report whose fact fields disagree with the recorded facts is refused. With no report contract it returns `credit`, `pending_handles` and the binding's current report facts.

## How it differs from its siblings

Compared with `hpc_job_execution` and `local_job_execution` (same parent):

- It works through a service's operations; the siblings run shell commands with one tool, `exec_command`.
- It may `wait` on a remote service job; the siblings are `tool` only.
- Its goal text is its own (service request identity, submission uncertainty, immediate response versus remote job). The siblings share the terminal execution text.
- Its prompt renderer is `render_api_launch_prompt`, chosen for API-launch contexts; the siblings use `present_native_task`, chosen for selected-execution contexts.
- Its credit and completion come from the API service executor; the siblings' come from the practical state of command receipts.
- Its live facts are the executor's facts; the siblings scan received and own handoff records.
- Yield profile class is `api_<service>..._handoff`; the siblings use `practical_<kind>..._handoff` or `..._outputs`.
- File layout differs: here `decision_state.py`, `decision_inputs.py` and `task_decision.py` are separate and helpers are split into small files (`execution_state.py`, `parent_input_custody.py`, `result_selection.py`, `retained_result_*.py`, `received_records.py`, `resource_information.py`); the siblings have `decision_context.py`, `decision_delivery.py`, `operations.py`, `result_records.py`, `received_information.py`, `internal_summary.py` and nine `terminal_*.py` files.
- `child_eligibility.py` here carries the note "pending explicit own-role specialization".

Much of the folder is role-generic code copied in. Branches for roles `launch`, `launch_local`, `launch_hpc`, `results`, `annotation` and `structural_homology_evidence` are present (for example in `from_parent.py`, `result_selection.py`, `received_records.py`, `report_reference_access.py`, `to_parent.py`, and the whole of `terminal_execution.py`). For this episode only the `launch_api` branch applies.

Same-named episodes exist in A102 under two other parents; their contents were not read. By file hash at `97308b94c`: `structural_homology_evidence/hpc_work_planning/execution_job_submission/api_job_execution` differs from this folder in `binding_record.py`, `episode.py` and `execution_contracts.py` only; `structural_homology_evidence/execution_job_submission/api_job_execution` differs in those three and in `parent_input_custody.py`, and has no `parent_launch_contract.py`. Every other file is byte-identical.

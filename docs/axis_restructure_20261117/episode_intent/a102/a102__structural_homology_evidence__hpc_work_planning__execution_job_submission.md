## What this episode is for

It picks which bound resource to run one permitted concrete execution request on. It then commissions the resource
child that runs the request and returns the usable handoff it gets back. Goal, verbatim from `goal.py`:

> Choose which permitted concrete execution request to commission on an explicit resource_id. Capabilities,
> recorded inventory and timing information inform the choice. Preserve the original job, immutable inputs,
> constraints and pinned instructions. A resource child owns iterative execution in the shared loop. Receive its
> requested typed handoff; no infrastructure chooses an approach. Actual received usable handoff completes this
> launch endpoint with exact zero future credit.

## Task and instructions

One unit is one model-selected action. The permitted common actions are set in `action_policy.py`:

- a native protein-structure results assignment: `tool` only;
- an `hpc` role among the ancestors (the case for this placement, under `hpc_work_planning`): `tool`, `child`,
  `redeliver_report`;
- otherwise: `tool`, `reason`, `child`, `wait`, `redeliver_report`.

`task.py` admits a `reason` selection against the reasoning envelope and the Store's reasoning schema. It refuses an
empty commit (`empty_reasoning_commit`) unless the commit declares `no_applicable_evidence` or the binding reports
task content. It validates every other selection against the selection schema. Rejected or invalid selections are
recorded as a decision effect `rejected`, with feedback. The categories are `action_contract`, `job_assignment` and
`report_format`, plus wait-target feedback. A `reads.map` parameter failure also carries a parameter-schema
diagnostic. The episode then admits the `report_update` into its interpretation form and validates it with grain
`launch`. The HPC handoff report validator (`library.hpc_handoff_report_contract.validate_return_contract`) is
attached to the task class.

`instructions.py` composes the instructions in this order:

1. the goal;
2. the reasoning-commit requirement, if reasoning is permitted;
3. the tool-knowledge and launch-instruction library instructions, if they are in the context;
4. the `pending_child_delivery` repair paragraph (select `redeliver_report` with a corrected form; preserve
   `current_report_update`);
5. the in-process child-wait paragraph (wait on a `pending_child_` handle, event `returned`, `after_cursor` 0,
   `reconsider_at` null; waiting earns no credit), if wait is permitted;
6. the `native_event_targets` paragraph, if native event information is configured and wait is permitted;
7. under the decision-exchange protocol, the history guidance is replaced by the `request_context` /
   `episode.history` wording.

## What it reads from its parent's assignment

The form is `execution_launch_assignment_v1` (`from_parent.py`, `parent_input_custody.py`, `execution_contracts.py`):

| Field | Meaning | Check |
|---|---|---|
| `version` | const `execution_launch_assignment_v1` | schema |
| `requests` | map resource_id -> concrete request, one property per bound resource, at least one | per resource: an API request schema (from the API service execution) or the practical `ASSIGNMENT_SCHEMA` with `resource_id`/`resource_kind` consts and `requested_job` alternatives (generic, native protein-structure tool contracts, resource-specific requested-job schemas); `_validate_request`: resource bound, kind matches, workspace confined, resource operation validator |
| `immutable_input_versions` | input version records | `validate_execution_input_versions` against the scope |
| `constraints` | `allowed_resource_ids`, `allowed_kinds`, `resource_id`, `kind` | lists of non-empty strings; `_permitted` filters resources by them |
| `launch_instructions` | pinned selection from the launch-instruction library | `SELECTION_SCHEMA`; materialised into `selected_launch_instructions` |

`prepare_assignment` checks the selection against the internal schema. When the parent role is `hpc` or
`hpc_execution` it authenticates the launch with the parent's `to_child_execution_job_submission.authenticate_launch`
(which lives in the parent's folder). It then validates every request, including API scope checks, the
protein-structure job inputs of each request and the immutable input versions. `required_return_sources` asks for
`execution_handoff_refs` only when the parent is `structural_homology_evidence` and the services report that an
annotation task is required. `initial_references` are the validated protein-structure job input references of all
requests.

## Decision state and what the model sees

`decision_state.py` reads a Store snapshot. The model sees: `goal`, `scope`, `working_state`, `visible_record_refs`,
`current_credit`, `current_evidence_vector`, an optional `investigation_progress`, `credit_binding`,
`time_accounting`, `pending_work`, `last_local_outcome`, `feedback`, `visual_evidence` (from the last completed
`image.view`), `report_deliveries`, `controller`, `controller_binding`, `tools`, `tool_knowledge`,
`job_episode_options`, `available_report_facts`, `requested_report_purpose`, `requested_form`,
`current_report_update`, `current_report_basis_refs`, `report_lifecycle`, and child reports. The episode's own
`decision_context` (`internal_summary.py`) adds:

- `execution_assignment`;
- `execution_progress`, the live report facts;
- `selected_execution_task`, only when every request is local with a `native_protein_structure` job and the
  services supply a scientific parent task. It holds the scientific question, the selected tool info, the requests
  with their resource information, the constraints, the selector and the result description.

`decision_inputs.py` adds:

- `resource_context` and `shared_information_context`;
- `launch_instruction_library` and `selected_launch_instructions`;
- `child_options`;
- the initial binding decision context;
- `completed_action_reports`;
- `requested_action_history`, in an HPC context;
- `pending_work`;
- `execution_expectations` for `launch`;
- `resource_tool_estimates` and `native_execution_expectations`;
- `waiting_support`;
- `contract_information_profile`.

`decision_provider.py` presents through `complete_with_presentation` with renderer `render_selected_execution_prompt`
when the context is a selected-execution context and not HPC, published-scientific or API-launch. Otherwise it calls
plain `complete(episode_id, 'REASONING', ...)`. The decision-exchange machinery (`decision_contracts.py`,
`decision_exchange.py`, `task_decision.py`) is a copy of the shared protocol.

## Tools it offers

`api_operations.py`: `execution.capabilities`, which reads the caller-bound resource configuration and the recorded
inventory, with no discovery. It returns `execution_resource_capabilities` (per resource: availability `unknown`,
tool names, workspace/policy/account/python/service/base_url, inventory snapshot, API configuration facts) and
`execution_initial_information`. For a protein-structure results assignment the catalog is the protein result
catalog. `resource_information.resource_tool_contracts` publishes the launch, result and native operation contracts
of every bound resource with commission routes (`entry_role` launch/results -> resource role). The resource work
itself belongs to the children.

## How its credit is counted

`credit.py`: credit kind `operational`. The live credit is
`handoff_unit × (number of distinct resource_ids with a usable received handoff, excluding resource_ids already
handed off in the initial known refs) + acquired_record_unit × 0.0`. The acquired fraction is fixed at 0 for
`launch`. The view also carries `new_handoff_count`, `new_acquired_record_count` and the binding
`execution_received_records_credit_v1`. Units are explicit, positive and finite (`configuration.py`), and the credit
is never bounded. After closing, `closed_credit.py` freezes the view inside the saved report facts
(`execution_closed_operational_credit_v1`, with context, binding, completion, archive, history and receipt-prefix
digests). Later reads return that original view and are never re-priced. Completion (`completion.py`) is a
`practical_completion_v1` proof: a completed own action whose `record_refs` include a usable handoff matching an
original request (endpoint `usable_handoff`, key `received_usable_handoff`).

## Continuation

`yield_estimator.py` requires `require_private_yield=True`.

- When eligible original requests are not yet handed off: a bounded controller (old `BoundedYieldController`), capped
  at `remaining = (#eligible requests not in initial handoffs) × handoff_unit`. Its cutoff and parameters come from
  the task yield profile keyed `launch:<sorted request classes joined by +>`. A request class is
  `practical_<kind>[_native_*]_<handoff|outputs>`, `api_<service>[_<algorithm>][_<database>]_handoff` or
  `compact_<version>`.
- When none remain: an exact-zero controller (`launch_original_request_exhaustion_v1`). Non-zero history raises.

In the new layout this maps to `yield_control` "completion with a target", with target = remaining request credit
(the bounded quality cap) and settings = the profile's cutoff and parameters. Choosing between the three estimators
is a porting decision. No new estimator is needed.

## What it reports to its parent

`to_parent.py` fact sources:

- `execution_handoff_refs`: authenticated handoffs;
- `execution_result_refs`: result acquisitions with windows;
- `execution_completed`: a boolean, true when any received handoff is completed;
- `execution_result_origin`: `NATIVE_RESULT_ORIGIN` when any window exists, else null;
- `execution_file_source_refs` and `execution_file_capture_outcomes`;
- the protein-structure fact sources, empty when not applicable.

`validate_report` requires every `x-source` field to equal the recorded fact. `report_delivery.py` builds the final
form from the saved interpretations and facts, saves it once and returns `{'form': ...}`. Without a report contract
it returns credit, pending handles and the current report facts.

Source: this episode's own files at commit `97308b94c` (40 Python files directly in the folder, 2,231 lines;
no `tests/`, `grading/` or `scoring/` folders). Old role name: `launch_api`. Old class `ExecutionEpisode`, task class

old `commissioning_parent` `structural_homology_evidence/hpc_work_planning/execution_job_submission`.

## What this episode is for

It carries out one assigned execution request through a configured API service, one operation per turn, until the
requested usable monitoring/results handoff is established from recorded service facts. Goal, verbatim from
`goal.py`, with `{service}` taken from the validated assignment:

> Carry out the assigned work through {service} using one selected operation each turn. Keep the original inputs,
> request, resource and parent constraints fixed. Choose useful preparation, service requests, observations or
> repair from the actual available operations and received outcomes. Distinguish an immediate returned response from
> a service job that continues remotely. Preserve the actual request or job identity and submission uncertainty; a
> missing reply does not establish that no job was created. Establish the requested usable monitoring/results
> handoff from recorded service facts. The configured controller governs continuation; verified original handoff
> completion gives exact zero future credit.

## Task and instructions

One unit is one model-selected tool action. Permitted common actions (`action_policy.py`):

- `tool`, `wait` when the assignment version is `api_service_assignment_v1` (a remote service job that keeps running);
- otherwise `tool` only.

It has no `reason`, `child` or `redeliver_report` action. `task.py` validates every selection directly against the
selection schema (the parent's reason branch is removed; only a bare `permits_common_action(..., 'reason')` call
remains) and validates report updates with grain `launch_api`. The HPC handoff report validator is not attached.
`instructions.py` is the same composition as the parent's: goal, then optional reasoning, knowledge, library, repair,
wait and native-event paragraphs, then exchange guidance. Because only `tool`/`wait` are permitted, only the wait and
native-event paragraphs can apply.

## What it reads from its parent's assignment

The assignment is one concrete API request, the `anyOf` of `_request_schema(resource_id, selected=True)` for every
bound resource of kind `api` (`from_parent.py`). The request schema comes from the API service execution, with
`resource_id` const and required. `prepare_assignment` does the following:

1. checks the selection against the internal schema;
2. validates the request with `_validate_request` and with `api_execution.validate_assignment(scope=...)`;
3. requires the role kind to equal the resource kind (`execution_resource_kind_conflict`);
4. requires the parent role to be `launch` (`resource_child_role_owned_by_launch`);
5. re-validates the parent's original launch assignment with `parent_launch_schema`;
6. validates the request's protein-structure job inputs and the original `immutable_input_versions`.

At initialise and before every tool execution, `_check_parent_inputs` re-reads the commissioning launch episode's
recorded `episode_assignment` and repeats those input checks. `required_return_sources` is empty.
`initial_references` are the request's protein-structure input refs.

## Children it may commission

None (`child_eligibility.py`: no child roles, no allowed children). It is a leaf.

## Decision state and what the model sees

The base decision state is the same as the parent's (`decision_state.py`). `internal_summary.decision_context`
gives `execution_assignment` and `execution_progress`, updated with the API service execution's own
`decision_context(context, view)` when it has one. There is no `selected_execution_task`. `decision_inputs.py` is as
the parent's, but captures `execution_expectations` for `launch_api`. `decision_provider.py` uses
`complete_with_presentation` with renderer `execution_prompt.render_api_launch_prompt` when the context is an
API-launch context that is neither HPC nor published-scientific. Otherwise it calls plain `complete`.

## Tools it offers

The catalog and execution are delegated to the API service execution configured for the resource
(`api_operations.py`: `self._delegate(context).catalog/execute`, after `_check_parent_inputs`). A protein-structure
results assignment uses the protein result catalog. The operation contracts come from
`api_execution.operation_contracts(resource_id, 'launch_api')`.

## How its credit is counted

Credit kind `operational`. The live credit is the API service execution's `credit_view(context, receiver_selection)`,
built with the same `handoff_unit` and `acquired_record_unit` passed at construction. A frozen closed view takes
precedence (`closed_credit.py`, identical to the parent's). Completion and verification are delegated to the API
execution (`completion_for_action`, `verify_completion`), with the recorded closed verdict checked first. Credit is
never bounded.

## Continuation

`yield_estimator.py` requires `require_private_yield=True`. It uses a plain `YieldController` with cutoff and
parameters from the task yield profile `launch_api:<request class>`. The class is
`api_<service>[_<algorithm>][_<database>]_handoff` for `api_execution_assignment_v1` / `api_service_assignment_v1`,
otherwise `compact_<version>`. The estimate comes from `PracticalYieldEstimator` over `verify_completion`, which gives
exact zero next gain once completion is verified. In the new layout this is the `yield_control` "completion with a
target" estimator, with the profile's cutoff and parameters as settings.

## What it reports to its parent

`to_parent.py` uses the same fact-source declaration as the parent. The live facts are
`api_execution.facts(context, completion_snapshot)` plus the empty protein-structure sources, with
`execution_result_origin: null`. `validate_report` requires `x-source` fields to equal the recorded facts.
`report_delivery.py` is identical to the parent's. The parent receives the form through
`from_child_api_job_execution.receive_report`.

## Differences from similar episodes

- Sibling `hpc_allocation_execution/execution_job_submission/api_job_execution`: identical except for its binding
  path, its commissioning parent and the import path of its own `terminal_execution`.
- Compared with `local_job_execution` / `hpc_job_execution`, it keeps the parent's file layout (`decision_state.py`,
  `decision_inputs.py`, `task_decision.py`, `execution_state.py`, `api_operations.py`, `result_selection.py`,
  `retained_*`) where those two use `decision_context.py`, `decision_delivery.py`, `operations.py`,
  `result_records.py` and the `terminal_*` files.
- It permits `wait` for service jobs; the native children permit only `tool`. Its prompt renderer is
  `render_api_launch_prompt`; theirs is `present_native_task`.
- It keeps a copy of the parent's `terminal_execution.py`, used only to build any local/hpc terminal behaviours that
  its configuration constructs.

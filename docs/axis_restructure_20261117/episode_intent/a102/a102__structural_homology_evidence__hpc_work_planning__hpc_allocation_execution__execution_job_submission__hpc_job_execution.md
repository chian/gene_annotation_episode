## What this episode is for

It is the execution agent for one assigned job on one HPC resource (configured kind `pbs_ssh`): it writes and runs the shell commands needed to prepare, submit and observe that job. Its goal, in its own words (`terminal_goal.py`):

> You are the execution agent for the actual job and resource assigned below. Use exec_command to write and run the shell code needed for that job. Choose scripts, environment preparation, software invocation and recovery from the actual resource instructions and observed results. No sequence of setup or job-stage operations is prescribed. Preserve the caller's scientific inputs, desired outputs and acceptance criteria. Historical inventory is context, not proof of present usability. Each command is one ordinary episode action: its actual result and earned credit enter the iterator, including failure or zero progress. Host bookkeeping records command versions and actual native job identities; do not maintain a parallel receipt ledger. If a submission outcome is uncertain, investigate that original submission rather than create a duplicate. Use the provided resource-specific instructions, account, storage and existing authentication route. workdir and env apply to the selected command only. target=resource runs on the assigned resource; target=coordinator runs in the local run directory for supplied-input and transport work. Both are ordinary journaled actions; resource computation belongs on its actual allocation. For coordinator-side transfers, execution_resource.ssh_argv, when present, is the exact configured transport prefix. Append the remote shell command as its final argument and preserve stdin. The supplied configuration gives the existing connection details. target=resource uses that transport directly. The episode iterator decides continuation from credit; add no stopping budget.

When the launch-instruction library has instructions for this resource, they are appended under "Resource instructions supplied from the frozen library:".

## Task and instructions

One unit of its cycle is one shell command. Each decision the model returns a `selection` and a `report_update`. A selection that fails admission creates no unit: the model gets feedback and decides again. A failed model call ends the episode's source as `source_failed`. A command whose execution raises is recorded as a failure outcome inside a `completed` receipt; a selected operation that raises outside that is recorded as a failed outcome; both enter the iterator with their credit.

Instructions are composed in `instructions.py`: the goal text above; the shared reasoning-commit requirement only if `reason` were permitted (it is not); tool-knowledge and launch-instruction-library instructions when present; the `pending_child_delivery` repair paragraph; wait and native-event paragraphs only if `wait` were permitted (it is not); and, under the exchange protocol, the `request_context` / `episode.history` paragraph.

Permitted actions (`action_policy.py`): `tool` only.

The prompt is rendered by this episode's own renderer `present_native_task` (`decision_presentation.py`) when the context is a selected-execution context and not an HPC, published-scientific or API-launch context (`decision_provider.py`). It presents the selected execution TASK, then STEERING, then "Current execution information".

## What it reads from its parent's assignment

- Its own assignment: one practical assignment (`practical_assignment_v1`) for one configured HPC resource, with `resource_id` and `resource_kind` = `hpc` fixed. Fields this folder reads: `resource_id`, `resource_kind`, `workspace` (must be inside the resource's configured workspace), `requested_job` (the generic job form, or a native job form the resource declares), `endpoint` (`usable_handoff` or `completed_job_outputs`), `constraints`, `initial_context`.
- What the parent may choose (`from_parent.py`): when the parent is a `launch` episode under an `hpc` ancestor, the choice is exactly the frozen HPC requests already in the parent's launch assignment that its constraints permit; if there is none it raises `frozen_hpc_launch_request_missing`. Otherwise the choice is any request matching a configured HPC resource's schema.
- From the parent's own launch assignment (`execution_launch_assignment_v1`): `requests`, `immutable_input_versions`, `constraints`, `launch_instructions`. The old code re-read it from the parent's recorded request before initialising and before every command and re-validated protein-structure job inputs and immutable input versions.
- From the request message: `initial_report`, `episode_assignment.launch_instructions`, `job_assignment`, and the report contract.
- Admission rules: the parent must have role `launch`; the selected resource must be of kind `hpc`; the resource's own operations must accept the assignment.

## Tools it offers

One tool (`terminal_contracts.py`), "identical for every resource":

- `exec_command`: "Execute the shell command you write on the assigned resource. Use normal shell/file tools to inspect files, author scripts, prepare an environment, run software, or submit/observe the actual job as needed. Returns its actual output and saved action receipt. workdir and env apply to this command; select them explicitly on each action." Arguments: `cmd` (a string or an argv list), `workdir`, `env` (all required), and optional `target` = `resource` (default) or `coordinator` ("local coordinator run directory for input-file work").

Running a command (`terminal_operations.py`): invalid arguments return an `invalid` outcome; the intent is recorded before execution and a completed intent returns its saved receipt without running again; an execution error becomes a recorded failure in the receipt; `cwd` and `environment` carry forward only when the command ran on the resource inside the assignment's workspace; the assignment's validations are assessed after every command; the receipt is published as a store record and returned.

## How its credit is counted

Credit kind is `operational`. The live credit is the practical state's credit view (`terminal_credit.py`): a projection of the assignment's requirement predicates over the initial validations and the saved command receipts, with fields `credit`, `initial_credit`, `operational_credit`, `requirements`, `satisfied_keys`. The projection function is in the practical-execution support code, outside this folder. Completion is a proof produced by the practical state when the assignment's completion keys are all satisfied by saved, validated receipts and the last receipt satisfies the endpoint predicate. After each command the task records the current credit view's `credit`. Once the episode has closed, the view captured at closure is the only credit returned afterwards (`closed_credit.py`). Nothing in this folder bounds, clamps or rescales the credit.

## Continuation

`yield_estimator.py`. The episode must have its own yield enabled (`require_private_yield`), otherwise it raises. It picks the profile named `launch_hpc:<class>` from `task_yield_profiles`, where `<class>` is `practical_hpc`, then any `native_*` keys of the requested job, then `handoff` (endpoint `usable_handoff`) or `outputs` (endpoint `completed_job_outputs`); a missing profile raises `execution_original_task_yield_profile_required`. Each profile is `{cutoff > 0, parameters}`. The old controller was `YieldController(epoch, initial_credit, cutoff, YieldParameters(**parameters))` with `PracticalYieldEstimator(verify_completion)`: a completion proof that verifies gives exact zero expected future gain. The instruction text says the same from the model's side: "The episode iterator decides continuation from credit; add no stopping budget."

Of the three current estimators, the one with this end state is completion with a target. The old code has no numeric target: it has the proof check over the assignment's completion keys. The port has to state what the target is.

## What it reports to its parent

The parent's typed form, filled with recorded facts and the latest admitted interpretations (`report_delivery.py`). Facts a parent may request (`to_parent.py`, `terminal_report.py`):

- `practical_completed`, `practical_receipt_digests`, `practical_receipt_refs` (the command receipts, published as records);
- `execution_handoff_refs`: received returnable handoffs plus this episode's own command receipts that are returnable handoffs for this exact assignment;
- `execution_result_refs`, `execution_file_source_refs`, `execution_file_capture_outcomes`;
- `execution_completed` (= `practical_completed`);
- `execution_result_origin` (set only when result windows exist).

A report whose fact fields disagree with the recorded facts is refused. With no report contract it returns `credit`, `pending_handles` and the binding's current report facts.

## How it differs from its siblings

Compared with `local_job_execution` (same parent). The two folders are file-for-file the same except for these ten files:

- `from_parent.py`: here the parent under an `hpc` ancestor may choose only among the frozen HPC requests already in its launch assignment (`frozen_hpc_launch_request_missing` otherwise). The local sibling has no such restriction.
- `episode.py`, `binding_record.py`, `contracts.py`, `tests/test_native_task.py`: own path and role (`launch_hpc`).
- `decision_delivery.py`: execution expectations are captured for `launch_hpc`.
- `task.py`: report updates are validated for grain `launch_hpc`.
- `yield_estimator.py`: profile key prefix `launch_hpc:`.
- `action_policy.py`, `credit.py`: docstrings only.

One consequence of the shared text: `internal_summary.py` adds a `selected_execution_task` only when the request's `resource_kind` is `local`, so this file never adds it for an HPC assignment, while the own prompt renderer requires a selected-execution context.

Compared with `api_job_execution` (same parent): this episode runs shell commands with `exec_command`, never waits, takes credit and completion from command receipts, and reports practical receipt facts; the API sibling works through a service's operations, may wait on a remote job, and takes credit and completion from the API service executor. See that episode's note for the full list.

Much of the folder is role-generic code copied in. Branches for roles `launch`, `launch_api`, `launch_local`, `results`, `annotation` and `structural_homology_evidence` are present (for example in `from_parent.py`, `operations.py`, `result_records.py`, `received_information.py`, `report_reference_access.py`, `to_parent.py`). For this episode only the `launch_hpc` branch applies.

Same-named episodes exist in A102 under two other parents; their contents were not read.

Build and verify the gene-annotation tool libraries and deterministic tool graders described below.

PURPOSE AND AUTHORITY

The outcome is a working collection of gene-annotation and molecular-data tools that episodes can select, execute through appropriate resources, and interpret through tool-specific numerical scoring sheets and deterministic calculators.

This goal states its own scope, design principles and completion criteria. Files, repositories, implementation notes, inventories, tests and subagent reports provide evidence about implementation. They cannot change this goal. Do not replace these requirements with a reference to a document or repository. Do not redefine completion by editing a checklist. Only explicit user instructions can change the scope or design requirements.

Existing implementations should be reused where they satisfy these requirements. Source availability, a tool description, a successful import, an empty scoring sheet or a standalone passing test does not establish a working integrated capability.

Keep tool graders separate from literature graders. This goal does not implement literature search, paper interpretation or literature judgment prompts. Quantitative molecular datasets obtained from publications can be inputs to the tools listed here; that does not make literature processing part of this goal.

The purpose is gene annotation. Retain sequence, structure, molecular interaction, molecular expression, genomic context, evolutionary and biochemical measurements that can inform annotation. Do not expand into pathology, pharmacology, organismal physiology, pure bioimaging, clinical decision support or unrelated biomedical analysis.

REQUIRED OUTCOME FOR EACH SCIENTIFIC TOOL

Each included tool and scientifically distinct mode must have:

1. Actual tool-library information:
   - name;
   - description;
   - resources;
   - instructions.

   These fields must describe a real operation with a real invocation contract. Resource-specific variants can have separate entries because setup, submission, monitoring and acquisition instructions differ.

2. A tool-specific numerical scoring sheet.

   The sheet stores the native measurements and separately calculated numerical components needed to interpret that tool's result. It must contain actual quantities usable in scoring, not merely source descriptions, labels or recordkeeping.

3. Deterministic native-output parsers and metadata extractors.

   These populate the sheet from retained results and explicitly supplied metadata. They preserve meaningful associations among sequences, hits, functions, taxa, samples, conditions, references and measurements.

4. Separate deterministic score calculators.

   These consume the populated sheet and explicit parameters. Individual numerical components and their combinations remain inspectable. Changing a formula or its parameters must permit recalculation from saved data without repeating the analysis or reacquiring its inputs.

5. Production integration.

   The selected tool must reach the correct child-owned execution operation. Its real result must reach the appropriate parser, sheet and calculators. The requested typed result must then reach its receiving episode through the existing communication boundaries.

6. Meaningful verification.

   Verify numerical answers, native formats, missing and partial data, relevant failure cases and the actual integration path. Record separately what was inspected, tested with synthetic fixtures, tested with retained native output, executed live and verified through episode communication.

Supporting acquisition, preparation, transfer and status operations need accurate typed outputs and deterministic validation. Do not manufacture an annotation-confidence score for downloading a file, creating an index, receiving a job identifier or observing process liveness.

KNOWN DEFECTS THAT MUST NOT PASS THROUGH THE NEW LIBRARIES

Where the included paths contain these behaviors, correct them before presenting their outputs as valid scientific measurements:

- Keeping only the first BLAST hit or HSP, discarding the native output, or calculating coverage from a gapped string length.
- Padding sequences after failed alignment.
- Returning a fixed placeholder phylogenetic tree after failure.
- Returning a zero contact matrix after failed data acquisition.
- Creating simulated clinical annotations or experimental observations inside a real-data operation.
- Replacing negative expression values with absolute values without a scientifically justified, explicit transformation.
- Calling reconstruction error “explained variance” or calling simple library-size scaling “TPM.”
- Consuming nonexistent ATAC intermediate files, duplicating paths or assuming equal depth factors.
- Comparing structural residues solely by integer residue number while ignoring actual sequence correspondence and insertion codes.
- Calculating concentration-dependent biochemical parameters without required calibration, concentration or volume information.
- Silently using uncompensated flow data, ambiguous channels or undocumented gates.
- Clamping negative measurements or background-corrected differences to zero without preserving the original values and explicitly defining the calculation.
- Replacing complete numerical results with rounded prose logs, top rows or truncated serialized previews.
- Corrupting identifiers during group creation or assuming that a partial download is complete.
- Hiding retries, resource changes or new submissions inside acquisition or grading functions.

DESIGN PRINCIPLES — REREAD THIS ENTIRE BLOCK AFTER EVERY TOOL

1. Preserve the episodic unit of composition.

   “Tools do tasks. Episodes are problem solving processes.”

   An episode owns iterative decisions within its assigned goal and scope. The information library helps construct the child's decision problem. Tool instructions support that process; they do not replace it.

   Do not create a LibraryEpisode, a new grading episode type, a complete handwritten episode for every tool or an autonomous workflow layer.

2. Preserve the three construction slots.

   The slots are evidence_axis, thought_pattern and child_tool_info.

   child_tool_info contains real tool information, including name, description, resources and instructions. A child can receive multiple tools selected for its investigation. Do not replace this with one tool_ref, names alone, a fixed bundle or a preconstructed complete episode.

   The parent needs appropriate names, descriptions and resource information to select tools. The selected child receives the corresponding substantive instructions and actual callable contracts.

3. Preserve episode ownership and resource decisions.

   The scientific parent supplies the job, scope, constraints and requested typed return. Launch chooses an execution approach where the parent leaves that choice open. API/service, local-compute and HPC episodes retain their distinct preparation, execution and monitoring structures.

   Infrastructure executes the selected work. It does not substitute resources, enlarge the task, choose retries or cancel work.

   Preserve independent execution, durable commissions and the shared method_loop. Do not hide an autonomous model loop inside a tool.

4. Keep tool information, numerical sheets and executable grading functions distinct.

   Tool instructions explain the operation and its appropriate use.

   The numerical sheet stores actual measurements and calculated components.

   Native-output parsers and metadata extractors populate the sheet.

   Deterministic calculators compute numerical components and their explicit combinations.

   These are separate responsibilities. Do not encode a second scoring language in prose or JSON when ordinary functions can perform the calculation.

   Tool grading does not redesign the evidence-axis sheets or the final annotation-score formula. It supplies typed numerical components that those separate consumers can use.

5. Define numerical meaning before calculating.

   For each numerical field, specify:
   - what is measured;
   - its exact input fields;
   - its formula or native source;
   - units;
   - population and denominator;
   - coordinate convention where relevant;
   - uncertainty when available;
   - missing-input behavior;
   - whether it is observed, predicted, fitted, normalized or otherwise derived.

   Preserve individual components before combining them through explicit sums, products or statistical models.

   Do not turn vague words into a single applicability, reliability or transfer score. Do not encode categories as numbers and describe them as measured confidence.

6. Prefer actual native measurements.

   Preserve native scores and statistical quantities where they exist. Do not replace alignment scores, coverage, significance, expression statistics, branch support or experimental measurements with an LLM impression.

   Preserve native ordinal classifications as classifications. A native model score is not automatically a calibrated probability of annotation correctness.

   Measured zero, missing, not measured, failed, truncated and incompatible are different states.

7. Preserve complete scientific data and associations.

   Retain the full native results required for present and later calculations: hit sets, HSPs, alignments, coordinate maps, matrices, trees, sample relationships, measurements and relevant metadata.

   Keep query–subject–function–taxon–source relationships intact. Keep gene–sample–condition–replicate relationships intact. Keep variant/reference and residue/model correspondence intact.

   Do not join independently sorted lists, pick an arbitrary first record or infer an accession relationship merely from a shared taxon.

   The retained artifact may be large. The episode-facing projection should be small and specific.

8. Separate acquisition from parsing and calculation.

   Native-output parsers, metadata extractors and calculators operate on supplied data. They make no network requests, submit no jobs, invoke no LLM and choose no resource.

   Additional information needed for a calculation becomes an explicit acquisition requirement for the responsible episode.

   Recalculating a saved sheet must not rerun the experiment or analysis, reacquire records or silently change reference data.

9. Distinguish scientific modes and actual formats.

   Pairwise correspondence and database identification are different questions. Different modes can require different sheets even when the executable name is the same.

   Select parsers using actual format, version, mode and declared fields. Do not select solely from API/local/HPC labels.

   Matching formats and mathematics may share implementation. Different meanings must retain their own contracts.

10. Make combinations inspectable and adjustable.

    Keep explicit model parameters and assumptions. Report which numerical components a combined score uses and which are retained but unused.

    Storing taxonomy, source-quality or uncertainty information does not establish that a formula uses it.

    Handle repeated representations, overlapping alignments, duplicate sequences, shared samples and dependent evidence explicitly. Different accessions or files do not establish independence.

    Population corrections require actual population measurements or explicitly declared assumptions. Returned hits alone do not establish database prevalence.

    Conditional function weights, model predictions and calibrated probabilities have different meanings. Name them accurately.

11. Preserve the BLAST distinctions already established.

    Pairwise BLAST grading measures residue correspondence, aligned positions, substitutions, gaps, query/subject coverage and relevant native alignment scores. Do not use database E-value as the basis for paired-sequence relevance.

    Database BLAST grading examines the returned hit population, not just the best hit. Preserve function assignments, complete alignment measurements, taxa, source provenance, duplication and relevant database-population information.

    Provide explicit, replaceable statistical calculations for candidate-function identification. Taxonomic agreement and dispersion, target-taxonomy compatibility, source quality and representation imbalance must be available as numerical components or explicitly missing inputs.

    Do not infer horizontal transfer merely from a scattered hit list. Preserve the measurements that allow the scientific episode to investigate that possibility.

    A cultured/closed-genome label and a metagenomic label are provenance categories. Use actual completeness, contamination, coverage, annotation evidence or other measured information when available; do not invent a universal category-to-confidence conversion.

12. Keep communication specific to the receiver.

    JSON is structured storage and an intermediate representation, not the complete model prompt.

    TASK contains detailed recurring instructions describing the actual assignment, objects, choices and constraints.

    STEERING contains concise decision-relevant facts and tables from received information and the episode's own prior work.

    Do not shorten TASK merely to make STEERING concise. Do not expand STEERING into a transcript, narrative summary, full scoring sheet or raw output dump.

    Parent-to-child communication contains the assigned task and necessary supplied facts, not the parent's yield history or private reasoning.

    Child-to-parent communication contains the requested typed information, with meaningful relationships validated against actual records. Do not add an LLM call to restate recorded facts.

    Within an episode, show decision-relevant action categories, observed yields, expected yields, uncertainty and specific prior attempts when needed. Internal lookups or additional model calls before the selected action completes do not create extra completed actions.

13. Keep monitoring instructions and tool information distinct.

    Monitoring uses the generic task instructions appropriate to the resource type.

    Tool-specific monitoring information identifies the actual launched operation, native states, logs, progress measurements and deterministic extraction functions. It is not a separate LLM judgment prompt for each tool.

    Results-library entries describe actual artifacts, parsers and requested numerical projections. They must not become vague “does this support the annotation?” prompts.

14. Preserve credit and continuation.

    Record actual outcomes before projecting credit.

    One completed own action supplies one local observation. Parsing, score calculation, report construction, statistical refresh and internal lookup do not manufacture additional turns or credit.

    Keep scientific investigation progress, annotation support, monitoring information, duration expectations and local yield histories distinct.

    Repeated retrieval, unchanged polling and duplicate delivery do not create new scientific progress. Child internal work does not become multiple parent observations.

    Preserve original forecasts and completed observations. New formulas or parameters do not rewrite historical results.

    The configured estimator/controller owns continuation. Add no hidden stopping rule, scientific acceptance gate, fixed turn cap, autonomous scheduler or mandatory polling itinerary.

    Validated completion of an original practical assignment sets future expected credit to exact zero immediately, preserving the final actual gain and prior observations. Use the ordinary controller comparison without an extra zero turn. This exception does not create a scientific truth/completion gate.

15. Preserve practical resource constraints.

    Keep local limits at 20 GiB RAM and 4 GiB scratch, with no invented wall-time budget.

    Do not run local database BLAST on this machine. Use the API or an appropriately prepared HPC resource. Local two-sequence tests remain distinct from database searches.

    Keep Aurora software, environments, databases, caches, inputs, temporary files, logs and runs under /lus/flare/projects/BioReason-Aurora-Test.

    Charge new Aurora PBS jobs to EpiCalib using -A EpiCalib.

    The only workflow file allowed in Aurora home is /home/chian/WORKSPACE_DIRECTORY.md. Do not create run directories, environments, caches or job outputs there.

    Work with the user on actual ALCF access and authentication when needed. Do not guess credentials, hosts or an unrelated scheduler. Aurora and Polaris are distinct deployments. A tailnet machine is not automatically an HPC deployment.

    A local client calling a remote API does not mean the scientific algorithm ran locally. Generic SSH, Parsl or Globus transport does not prove a tool is deployed on a resource.

16. Report implementation honestly.

    Distinguish source present, prerequisites present, invocation bound, native format observed, parser tested, calculator tested, live execution verified and complete episode-path integration verified.

    Do not call work complete because a descriptor exists or tests that bypass the real path pass.

    Unknown capabilities remain unknown. Unavailable credentials or native formats remain explicit unfinished work for the affected entries.

    Preserve permanent user decisions. Record corrections additively rather than silently replacing earlier records.

Read it verbatim. Do not substitute:
- a remembered summary;
- a shortened checklist;
- a mutable design-file copy;
- a subagent's paraphrase;
- upstream documentation;
- the implementation's existing behavior.

Then reread the current tool's agreed input/output and scoring-sheet contract before declaring that tool complete.

After substantial external documentation or native-output examination, perform the same reset before translating what was learned into the scoring sheet and calculators. External material supplies facts and methods; it does not override the user's design.

Every coding subagent must receive this requirement and the relevant original constraints in its fresh task context.

This is an implementation discipline. It is not an episode action, runtime gate, additional model request in the deployed workflow or source of credit.

REQUIRED NUMERICAL CONTENT BY RESULT FAMILY

The exact sheets must be developed from real outputs, but they must cover these concrete measurement families:

- Alignments: paired and identical positions, substitutions, gaps, spans, coordinate correspondence, coverage with explicit denominators and native scores.
- Database identification: complete hits, explicit function assignments, duplicate/dependence groups, taxonomic structure, source measurements and actual database-population information when available.
- Gene prediction: intervals, strand/frame, partial boundaries, translation and native prediction quantities.
- Profile/covariance searches: sequence and domain scores, significance, bias, coordinates, model coverage and native reporting/inclusion information.
- Multiple alignment and phylogeny: sequence membership, site correspondence, gaps, conservation, branch lengths, support, function composition and comparison with supplied organismal relationships where requested.
- Structure comparison: actual residue correspondence, matched coverage, superposition measurements and uncertainty/confidence attached to the input structures.
- RNA structure: base-pair correspondence, structural features, energies and native uncertainty where produced.
- Variants and copy number: alleles, coordinates, depth, support, quality, reference identity and segment measurements.
- Chromatin/regulation: motif scores, interval relationships, peak statistics, contact counts, normalization and actual comparison populations.
- Expression and molecular abundance: original and transformed measurements, sample/replicate design, contrasts, effect sizes, variability, significance and normalization.
- Enrichment: foreground, background, overlaps, tested population, native statistics and correction method.
- Biochemical assays: raw signals, calibration, concentrations, rates, fitted parameters, residuals, uncertainty and sample-to-target correspondence.
- Assemblies/bins/read QC: sequence/read denominators, coverage, ambiguity, contiguity and actual completeness/contamination measurements.
- Pathways and complexes: explicit component membership, presence/absence denominators, molecular associations and model constraints where applicable.

A result family is not a license to invent a universal scoring formula. Each tool's concrete fields and calculations must be defined and verified.

RESOURCE AND LIBRARY INTEGRATION

Populate the launch, monitoring and results information required by the included tools.

Keep resource-specific instructions separate where execution differs. Reuse parsers where native formats genuinely match.

For every required operation, record the actual usable or intended resource route:
- API/service;
- local compute within the stated limits;
- HPC through a configured environment.

Do not pretend every operation exists on every resource. Do not silently remove a required operation because its resource is unfinished. Report the exact missing dependency, access requirement, format or binding.

Prepared software and databases may be reused through the existing practical execution design. An inventory description or matching inventory hash does not by itself prove that an executable, database or service is currently usable.

Do not restore scientific execution tools to the root to solve a missing binding. Connect selected work through the appropriate existing child ownership.

PLANNING AND PARALLEL IMPLEMENTATION

Define modular boundaries before assigning coding work.

For each workload, specify:
- exact tools and modes;
- owned files;
- input artifacts and native formats;
- populated sheet fields;
- parser/extractor signatures;
- calculator signatures and parameters;
- metadata joins;
- return and failure shapes;
- actual consuming functions;
- required verification examples;
- handoffs to other workloads.

Dependencies must name the exact required output or interface. Do not declare entire groups blocked merely because their final results are nested or composed.

After those contracts exist, use fresh subagents in parallel for independent tool families, formats, calculations and integration work. Give them explicit, nonoverlapping ownership and the relevant verbatim constraints. Do not reactivate an unrelated old task with stale context.

Shared parsing and mathematics should be shared because their semantics match, not because the tools happen to appear in the same source module.

ACCOUNTING AND COMPLETION

Maintain a fixed row for every required tool/mode and resource binding. Retain completed rows.

Track these completion fields separately:
- tool information and invocation contract;
- numerical sheet;
- native-output parsers and metadata extractors;
- deterministic calculators;
- production result-path binding;
- numerical and integration verification;
- live-resource verification status.

Preserve mappings for aliases and shared implementations. Splitting a row into modes must retain its original identity and explain the relationship. Do not silently drop unfinished entries or merge them under a broader heading.

For each scientific tool, provide a filled numerical example whose values can be checked. Include relevant cases involving missing data, zero results, partial output, malformed output, wrong references, coordinate boundaries, duplicates, overlapping observations or inconsistent metadata.

Verify saved-sheet recalculation without network access or rerunning the tool.

Verify the complete selected-tool → correct resource child → native artifact → populated sheet → deterministic calculations → requested typed return path.

Print concrete examples, actual verification results and remaining work in the conversation. Do not send the user to files instead of providing the information needed to steer.

## Publication, returned receipt and failures

Before publication, close/checkpoint only destination connections as needed, then verify independent main working DB rows and explicit new source/artifact delta. Never checkpoint the source. Fsync all newly written artifact/snapshot/manifest/authority/receipt files and their directories. The immutable checkpoint/schema/artifact/reference manifests identify exact contents; receipt records original authority/hash/counts, zero-write checks, fixed identity, original raw pending hash, lineage IDs and explicit initial list. A result wrapper hashes the final canonical-JSON-plus-LF receipt file; the receipt does not contain its own hash. The workspace DB hash is explicitly observed at publication and is expected to change under later authorized caller work.

Publish by Linux renameat2(RENAME_NOREPLACE) using the pinned parent directory fd, with no fallback that overwrites or follows a replaced parent. Recheck parent path inode and destination nonexistence first; atomic no-replace closes the race. After rename, fsync parent, then return the closed result. Unsupported no-replace capability fails with a retained stage; do not use os.replace. No automatic resume/reuse/merge/overwrite of a prior destination, even an apparently matching one.

ScientificCheckpointForkError.as_record returns the exact closed failure shape. affected_refs contains only finite paths/IDs, never raw request bodies/tokens/private exception prose. Source unchanged is true only after completed before/after checks, false on observed change, null if not verified. Before stage creation, staging/published paths are null and publication_state not_created. A pre-rename failure retains its stage at the actual current parent-fd location and reports retained_stage. If rename succeeded but parent fsync failed, report published_durability_unconfirmed and the actual published path, not a nonexistent old stage; do not return success or remove/overwrite it. Writing optional custody-failure.json inside an existing stage is best effort, exclusive/new and cannot hide the primary error. Abrupt process kill may leave only a partial private stage and no failure JSON: it is untrusted partial output, not a usable fork or success. No cleanup deletes valid partial work, source files or a raced destination.

Future local publication is only of a NEW private workspace/receipt, not a permanent repository/public evidence release. Any later safe public capsule requires a separately reviewed export: raw scientific requests/DB/artifacts are not automatically public, original paths/hash mappings must stay truthful, and renamed/redacted derivatives get new identities. There is no hidden runtime scientific gate; these are custody implementation/precondition failures.

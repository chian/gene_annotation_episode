## 2. Concrete source-only byte-access bypass

Let `S` be an actually received utility source with provider `episode.execution_result` and version `native_blast_utility_bundle_v1`. A selected status/sequence/context return can legitimately carry top-level source_ref `S` while returning no artifact/saved-data facts. The source record contains `artifact_ref=B` for the original bundle and may retain stdout_ref/stderr_ref and auxiliary artifact references. Under `NativeBLASTUtilityResults.retained_reference_access` at 476, access to S can be granted while access to B is false. The explicit return path correctly does not grant B.

The currently inspected material path bypasses that distinction:

1. `scientific_process_episodes.execute` at 501 validates selected tool arguments and passes `permitted_record_refs=context.received_record_refs` only for `result.blast.hsp` at 539. It does not authenticate a utility source's selected byte operand for material/source tools.
2. `WorkflowServices.execute_tool` at 54 forwards optional permitted refs without applying a utility artifact check. `ToolRegistry.execute_async` at 490 installs them, and `_execute_operation_async` at 522 returns an existing saved operation before `_perform`, except its existing special source.locate/HSP checks.
3. `tools.py:1369` calls `store.register_material(source_ref=S, ...)` for material.from_source. `materials.register_material:188` accepts the registered source at 198 and returns a material wrapper at 222. It retains S's identity and does not itself open bytes, but creates a future handle to B without checking B's grant.
4. `tools.py:1374` calls `store.parse_material`; `materials.parse_material:228` resolves that material to S at 237 and calls `artifact_path(store, S.artifact_ref)` at 239. `artifact_path:130` hashes/opens B; subsequent parsing reads it at 256. The source-only receiver has now obtained an operation on unrequested B. `materials.read_material:445` likewise reads S.artifact_ref at 451 and returns base64 content. Existing cached parse/tool outcomes can bypass any check placed only after these dispatches.
5. `tools.py:1462` calls `materials.source_window` directly for source.read. At 460-476, representation stdout/stderr selects the corresponding source reference; text uses text_ref when present and **falls back to artifact_ref** when absent; original selects artifact_ref. The function opens and returns text bytes without the utility provider's receiver-specific artifact grant.

This is an actual source-level consumer gap, not an allegation that new VDB facts create a new grant, and not runtime verification of an exploit. The same source shape exists for historical utility returns; preserve their old form bytes while fixing this direct consumer behavior.

### One shared existing check, five enumerated entrypoints

Root's proposed service method is:

```python
WorkflowServices.authenticate_material_source_operands(
    context: BindingContext, tool_name: str, arguments: dict
) -> None
```

Declare it in `EpisodeServices` and invoke it from scientific_process.execute after normal selected-tool/argument checks and before `services.execute_tool`, including before a saved-operation replay. It resolves only registered metadata to find the **actual selected byte artifact**, then calls the existing utility provider's `retained_reference_access(context, artifact_ref, "artifact")`. This is the single existing access decision, not a new permissions framework or approval layer. False rejects, existing explicit grant permits, non-utility sources retain ordinary behavior. Provider absence cannot turn a recognized utility-bundle source into an unguarded read; it must return an ordinary structured unsupported/unavailable operand failure.

The exact entrypoints/metadata lookup are:

| Tool | Resolve without opening bytes |
| --- | --- |
| material.from_source | arguments.source_ref -> source.artifact_ref, before registering a reusable wrapper |
| material.parse | arguments.material_ref -> material.source_ref -> source.artifact_ref, before cached parse or raw parsing |
| material.read | same material/source/artifact chain, before returning raw window or saved tool result |
| source.read | arguments.source_ref -> exact representation; stdout/stderr to respective ref; text to text_ref if present else artifact_ref; original to artifact_ref, matching source_window defaults/fallback |
| source.locate | arguments.source_ref -> original artifact_ref or text_ref, **without** fallback, matching received_source; absent text remains unavailable |

The check is narrow to a utility bundle source and its selected representation. Do not deny ordinary independent/caller material or extend a source grant to all auxiliary artifacts. Explicitly selected stdout may be readable while original bundle remains denied. Conversely, explicitly selected bundle or independently supplied original artifact stays valid under the existing provider check. A wrapper's ID alone does not establish a byte grant; recheck its original utility source on parse/read so historical wrappers and saved operation replay cannot bypass the corrected consumer.

`source.locate` has a separate preexisting bound-input requirement. `source_locations.received_source:31` rejects `permitted_inputs=None` with `source_location_inputs_not_bound`, requires source_ref in that list, then checks original source metadata/scope/ancestry before locating bytes. Scientific dispatch currently supplies None for this tool, so it is unavailable there even for a received source. Root should forward context.received_record_refs for source.locate as well as HSP. That permits the existing known-source check; the shared helper still separately checks the selected utility artifact. Merely forwarding source_ref would otherwise grant the original/text representation through the locate implementation. Do not add text fallback or alter source.locate's bounds/UTF8/identity checks.

Root owns the service, protocol, scientific dispatch and focused tests in its 666 partition. No change to material parsing numerical/format behavior, Store registration semantics, result publication or root tool catalog is required for this narrow port. Test source-only denial, explicit selected representation success, default text fallback, unavailable text in locate, historical wrapper/saved operation replay, and unaffected ordinary material. The helper must run before acquisition/format detection or cached-operation output, not after bytes were read.

## 3. Library consumers and scientific reuse

The result-side library binding is the existing resource commission path: actual tool information selected through child_tool_info -> original parent-defined execution assignment -> the chosen local job -> selected results child with selector/typed form -> authenticated immediate-child return. Root's `ExecutionBinding.resource_tool_contracts`, `WorkflowServices.tool_information_catalog`, native utility bindings and `execution_progress.describe_target` consume the exact new job/selector/fact union. They do not install a standalone root blast_vdb_cmd tool or a new grading process.

A later actual VDB search can use an explicitly selected four-column stdout artifact as metadata through existing `native_blast_database_metadata.py`:

- `native_blast_database_vdb_metadata_v1` has exact `documents` plus searches with a **real existing search_key**, `dataset_records`, `member_bindings`, `sequence_identity_bindings`, `sequence_proofs`, `feature_bindings`, `reference_metadata`, `population_records`, `parsed_sources`, `metadata_bindings`.
- `_PARSED_SOURCE` at 198 uses document_key, parser (`runinfo_csv`, `blast_vdb_cmd_table`, `ncbi_gbseq_xml`), source_version and nullable extraction_context. The current table extraction context at 194 requires dataset_key, selected_input, snapshot, entry_identifiers, native_returncode, producer_complete, include_filtered_reads, reference_selection, exact four-column outfmt and source provenance.
- `_vdb_dataset_matches:1612` verifies actual search operand, manifest snapshot/release and selected search options. `_vdb_units:1649` reads the **explicitly bound** document bytes, compares extracted dataset context, invokes the existing selected-entry parser and binds actual metadata, then populates the existing common VDB search sheet. It is a scientific search consumer, not a utility projection function.

Therefore this utility return does not automatically construct one of those metadata payloads, invent search_key/query context, fill RunInfo/reference/sample evidence, or treat a provenance artifact as a received document. The scientific episode must already own the real search and expressly bind an artifact it received with adequate supplied context. Current legacy parsed_sources extraction supports specific entries; all-mode output cannot be passed to it as an invented literal entry `all`. If later scientific all-mode reuse is required, it needs its own precise existing-search adapter contract; this supporting return task does not silently broaden that parser or score.

The common result artifact selected by saved_data=result is `blast_sequence_extraction_v2` or `blast_database_inspection_v3`, not the legacy parsed_sources input schema. Consumers must select the raw four-column output artifact when they intend that existing parser, or use an explicitly implemented typed common-record consumer. The utility's native lengths/counts/path observations are supporting facts and never a completed VDB search/annotation score.

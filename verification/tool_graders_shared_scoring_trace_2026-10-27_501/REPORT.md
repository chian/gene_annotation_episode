## Confirmed finding

The current NCBI BLAST API publisher retains the common database sheet but publishes HSP identity and endpoint-span coverage through a second implementation. `ToolRegistry._import_blast` builds `grade_blast_result(..., mode="database", resource="api", output_format="json2")` once, retains that grading with the original source, then calls `blast_search.hsp_row` for the observation values. `hsp_row` does not consume the sheet. This is an active consumer defect, not an orphan function or merely a different envelope schema.

Source-derived example, not executed: a four-column HSP with `qseq="ACGT"`, `hseq="AGGT"`, reported `identity=4`, `align_len=4`, valid endpoints 1..4, lengths 4, and valid native scores yields published `identity_fraction=1` in `hsp_row`. The same result's common `alignment_components` retains reported identity 4, measures 3 identical pairs, returns `fractions.alignment_identity=0.75`, and records `reported_count_traceback_conflict`. Both reports describe the same HSP. Publication should consume the already-built common sheet, preserving the reported count and conflict separately.

The independent span fractions are also real duplicated arithmetic, but they must not be replaced with paired coverage under the old names. For `AC-GT` against `ACAGT`, lengths 4 and 5, full endpoint spans are 1 and 1, whereas paired coverages are 1 and 0.8; alignment identity is 0.8 and paired identity is 1. The shared component needs explicitly defined span cells if the existing span aliases remain public.

## Complete BLAST publisher/consumer trace for the confirmed defect

1. `NCBIBlastService.publish` validates the selected fetch and original submission RID and builds the native request; `publish_existing_acquisition` records the selected operation and transaction. Neither calculates scientific numbers.
2. `ToolRegistry._import_blast` validates native identity, preserves archive/member bytes and native program version, invokes the common grader, and passes it to `_source`.
3. `_source` calls `retain_tool_grading`, saving `tool_grading_artifact_v1` beside the exact native artifact. `source_tool_gradings` checks provider and native-artifact custody on retrieval. These are retention/read helpers, not scoring implementations.
4. `_import_blast` loops original hit/HSP arrays and calls `blast_search.hsp_row` to publish comparison observations with `native_blast` original ordinals and original endpoint/frame/unit metadata. Independent HSP projection errors preserve valid siblings. The common sheet is not consulted for these numbers.
5. `blast_result_views._original_hsp` is the only other production caller of `hsp_row`. It reloads the exact original source, validates native hit/HSP address, query/reference identity, intervals and original submission RID, calls `hsp_row` again, and compares the observations against that recomputation. Thus changing only `hsp_row` can invalidate historical observations. This reader is active, not a test-only consumer.
6. `read_blast_hsp` returns the saved measurements and a bounded native alignment view. Its site grading uses the separate shared correspondence/site path. `blast_hsp_facts` copies existing observation values into `BLAST_HSP_FACT_SCHEMA`; it does not call `hsp_row` or recalculate identity.
7. `api_service_execution` obtains `blast_hsp_facts` when the selected requested return source is `execution_blast_hsps`; `execution_episodes` declares that typed form source and `execution_progress` binds the fetch extractor to `_import_blast`. The duplicate values therefore reach requested child returns. These paths do not implement W05 annotation-credit aggregation.

Search across production and tests found exactly two `hsp_row(...)` call sites: `_import_blast` and `_original_hsp`. Existing `public.blast.search`/collect source paths also route through `_import_blast`; their source presence is not a new assertion about current episode admission or live execution.

Important locator defect for the repair: `parse_blast_json` stores each original hit's `hit_index`, but compacts non-object HSP rows out of `hsps` without recording their original HSP ordinals. The database sheet keeps `hsp_components` in that compacted order. An original native ordinal must not be used as a list index into the compacted sheet. Add an explicit original-address map in common parsing/sheet population; do not join sorted/filter-derived arrays. The report-collection parser already has a `row_map` concept, but this report does not prescribe importing that entire parser into API publication.

## Other bounded findings and limits

Two additional active duplicate-component paths were read, but they are outside the immediate BLAST repair contract:

- `acquisition.parse_hmmer` independently computes native endpoint-span fractions. `_publish_hmmer_domain` publishes those legacy `query_coverage`/`target_coverage` aliases alongside common `model_span_coverage`/`sequence_span_coverage` values from `api_domain_scores`. The shared API/native HMMER sheet and calculator are correctly reused; the publication aliases still have an independent numerical authority. With valid identical input they can agree, which does not make the second implementation necessary. No executed divergent HMMER fixture or full alternate-route regression audit was performed.
- `sequence_ops.align_pair` calculates convenience identity/coverage and `_align_one` publishes those body fields alongside the common Biopython grader's measured/calculated fields. The two operation wrappers share the exact grader, but these convenience publication fields still duplicate component calculation. No executed mismatch fixture was performed. Refactoring should project aliases from the already-built common scores with their exact meanings preserved.

BLAST's `alignment_components` and the Biopython column calculator contain similar elementary counting/fraction work. That observation alone does not establish that a full BLAST HSP-set union analysis and a selected local/global Biopython alignment need an identical top-level sheet. A future shared residue-correspondence component could be appropriate; equivalence of all modes was not established here. HMMER vs Infernal is likewise not one scientific analysis simply because both perform searches.

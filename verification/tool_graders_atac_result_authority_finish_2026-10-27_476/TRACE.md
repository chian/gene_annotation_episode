## Verification method and limits

`run_checks.py` has distinct `launch`, `status`, and `collect` operations.
Each launch uses a new immutable source/test snapshot, a copied complete
installed site-package closure, and a copied interpreter. From check003 onward
the standard library is also copied and pinned. Tests execute through the
existing `local_jobs` / `native_lifecycle` with 20 GiB RAM, 4 GiB scratch,
zero swap, and no wall-time budget. Collection uses the original handle and
requires terminal, quiescent state; before/after digests remain in that attempt.
Host imports are limited to the existing lifecycle bootstrap. No application
test is run directly in the host shell.

The operand tests use authored opaque BAM and software identities. The return
tests use real Store, Journal, EpisodeReceipts and typed forms with an explicitly
strict synthetic result host. The production receipt tests use the production
result host and receipt validator with authored native lifecycle observations;
they do not run MACS2. Isolated origin/completion/dedup assertions are explicitly
labelled authored controls. They do not establish native measurement or full
model-owned workflow integration. Native producer, finite worker, and root
full-path evidence belong to their separately recorded packets.

The original 471/check001 was inspected through its original lifecycle handle,
not relaunched. `ORIGINAL471_STATUS.json` records terminal, quiescent return
code 1; its original runner did not retain dependency pins. The separate
471/collect attempt arose when a launcher was mistaken for a collector and
pytest received `check001` as an invalid path; return code 4 is not verification.
Neither earlier failure is reclassified as a successful check.

Per-attempt outcomes and current remaining limitations are recorded in
`RESULTS.md` after collection.

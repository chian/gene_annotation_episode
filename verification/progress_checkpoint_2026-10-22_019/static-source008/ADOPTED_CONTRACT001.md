**B. Exact deterministic keys and protocol recovery**

The direct helper exports pure:

```python
def direct_operation_key(*, registry_ref: str, job_ref: str,
                         parent_operation_key: str, operation: str,
                         ordinal: int, page: int | None,
                         page_size: int | None) -> str: ...
```

Inputs are nonempty stripped strings without controls; ordinal is a nonnegative exact int (not bool). The operations are submit/status/result/recover_submission. submit and recover use ordinal0 and both selector fields null. status uses ordinal0… and selectors null. result uses ordinal0, page1, original positive exact-int page_size. Invalid operands raise `ContractError('direct_hmmer_protocol_arguments_invalid')` before any storage or transport.

Compute `D=sha256(canonical({version:'ordinary_hmmer_protocol_key_v1',registry_ref:R,job_ref:J,parent_operation_key:K}).encode('utf-8')).hexdigest()` using actual `domain.canonical`, preserving all64 hex characters. The key is **exactly** `ordinary-hmmer-v1:D:OP:N:P:S`, replacing null P/S with `-`, with decimal integers having no leading zeros. Example suffixes are `:submit:0:-:-`, `:status:0:-:-`, `:result:0:1:20`, `:recover_submission:0:-:-`. The outer K remains the argument to `operations.order`, preserving the existing `provider_job_reference(K,request)`. Child phase keys are operational identities, not new actions or physical search attempts.

The readable suffix is deliberate: from `inspect(J).latest_operation_refs` and `read_operation`, the helper parses only keys with this exact D prefix, checks each receipt's operation against OP, rejects malformed own-prefix keys, and validates contiguous status ordinals0…n−1. Foreign prefixes belong to other explicit own operations and are ignored for this invocation's cursor. A missing ordinal followed by a higher committed ordinal, duplicate ordinal/key conflict, result with the wrong selector, unexpected submit in a collect prefix, or any status after an earlier terminal status/failure is `ContractError('direct_hmmer_protocol_identity_conflict')`. No new cursor table/port is needed.

Protocol for a search:

1. Prepare the actual selected operands with existing shared preparation and normalized current scope; call `order` with K. Do not call `RemoteSearches.search` after order. Call `submit_once` only with its one original submit key and `retry_of=None`. Replaying an existing original claim imports its capture or returns original uncertainty; it never chooses another POST.
2. Before further HTTP, return any already committed terminal failure/result for this exact prefix with its original mapping. A later different action's success cannot rewrite this prefix's committed failure. Otherwise, if an original first-page result is already cached, validate its actual result receipt/snapshot through public ports and select `result_once` at this prefix's result key to reuse that body, with no status GET, matching the ordinary cached-collect shortcut.
3. Without a first-page cache, consume the original contiguous status prefix. Completed pending receipts replay without HTTP or sleep. A recorded SUCCESS advances to the original result key. A receipt failure or completed FAILURE/REVOKED becomes the structured original operation failure, with no new status key. `outcome='completed'` alone never establishes search success.
4. At the first uncommitted status ordinal call `status_once_with_origin` at that exact key. It can finish the original retained capsule, return its receipt or acquire this one new protocol read. Only for a valid completed pending state PENDING/RECEIVED/STARTED/RETRY **and origin worker_dispatched** call the existing `asyncio.sleep(remote_searches.poll_interval_seconds)` once before the next status ordinal. For capture_reused/receipt_reused, do not re-sleep. For terminal/failure/no_capture, do not sleep or automatically repair/retry. Crash during/before that sleep resumes immediately, as existing ordinary `collect` does on a fresh process. No invented elapsed sleep, deadline, jitter, exponential backoff or cap is introduced.
5. Call `result_once` for original page1/size at the original result key. A saved result receipt/capsule is reused. A failed result is terminal for this prefix; no new result key is manufactured to retry it. A new selected collect action can attempt its own originally selected protocol work.

Protocol for collect: after original public.hmmer provider/subject/scope checks, call classify_order. Only unregistered/null uses the unchanged legacy collect; no timing fields are emitted. Registered work is never ordered again. With no known remote handle, `recover_submission` at this collect prefix's recovery key may import the original claim/capsule only; it sends no POST. Missing claim, original not_sent, ambiguity or unfinished submission returns its meaningful existing structured result, not automatic submission/retry. Then apply the same cached-page/status/result rules above, with this **new collect K**. A cached first page avoids GET. Timing recovery/source publication on this new selected collect may succeed without changing the original search's saved result. `public.hmmer.page` remains untouched and never uses this result cache as a replacement for its selected fresh GET.

`ProviderOperationInProgress` becomes an ordinary **failed, explicitly in-progress tool outcome** with code submission_in_progress, original job/operation key and no terminal provider receipt. It does not mean the underlying provider operation terminated. Use `AcquisitionError` with this code, phase`provider_operation`, job_ref and operational operation_key; do not let it become generic adapter_execution_failed, completed science, a new retry or an additional observation. The already running capture continues. The outer tool result, once saved, is immutable; future repair requires a separately selected collect. Cancellation is different: propagate `CancelledError` without manufacturing a terminal outer result; the existing shielded capture and original keys permit replay recovery.

Provider receipt failure maps to `AcquisitionError(failure['code'], retry_after=failure['retry_after_seconds'], job_ref=J, snapshot=read_snapshot(ref) if present, phase=failure['phase'], submission_outcome=failure['submission_outcome'], operational={'cause':deepcopy(failure),'provider_operation_ref':ref})`. The cause remains the original closed failure, preserving native_code/http_status/diagnostic/snapshot/affected refs. Completed FAILURE/REVOKED status with no failure object maps to existing code remote_search_failed, phase status_response, original snapshot/ref/state. Local membership storage/incomplete/conflict failures map to failed local_preflight AcquisitionError with the exact membership code, not legacy fallback. Unknown_job maps to ContractError unknown_job. This adds no provider receipt or remote attempt. Existing ToolRegistry error feedback preserves these values.

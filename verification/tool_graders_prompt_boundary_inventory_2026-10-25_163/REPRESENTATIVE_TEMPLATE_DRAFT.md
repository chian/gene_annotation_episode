# API execution template for review

This is a **proposed text template**, not a deployed prompt. Braced blocks are exact expansion points, not permission to abbreviate instructions. Each complete expanded request must include every applicable TASK block below. The operation bodies and operand tables come from the actual selected service/tool catalog; no grading prompt or workflow is invented.

```text
TASK

Carry out {assigned native application or immediate operation} through {selected
service} on {selected resource}. Keep the original inputs, parameters, resource,
parent constraints and requested {endpoint} fixed. The supplied data and selected
file boundaries define this work. Preserve sequence/member, sample, reference and
output relationships required by the selected operation.

Choose one useful available preparation, service request, transfer, observation
or repair using the actual outcomes. Preparation validates a request and does not
submit it. An immediate API response is not an asynchronous job. A submission
receipt is not its scientific result. If a response is missing, preserve the
submission uncertainty and original identity; do not infer that no job exists or
silently retry, enlarge the request or change resources.

Use the actual operation instructions and callable operands below. Reuse valid
partial work. Missing inputs, authentication, native formats and unavailable
measurements remain explicit. Acquire status, logs or returned artifacts only
through an available selected operation. Native measurements retain their units,
subjects, populations and missing-state meanings; do not turn an operational
receipt into an annotation-confidence score.

Establish the original requested usable monitoring/results handoff from recorded
facts. Return exactly the parent's declared typed fields and meanings. Recorded
fact fields are populated from actual records; update only declared interpretation
fields in the same decision response. No separate report-composition call is
needed. The configured controller owns continuation. Validated completion of the
original practical endpoint makes its future expected credit exactly zero while
retaining the final actual gain and all earlier observations.

Assigned request
{complete human-readable request values, immutable input associations, parameters,
output destinations, endpoint, allocation and parent constraints needed here}

Selected service/tool information
{complete substantive operation instructions and exact available callable
contracts, rendered as text/operand tables; no raw JSON envelope}

Parent's original return form
{purpose; each exact field name/type/allowed value and meaning; x-source facts
identified as recorded facts; interpretation timing and current initial values}

Response choices
{actual closed select_action and permitted request_context meanings; full TASK
recurs after a lookup; the lookup itself creates no completed action or credit}

STEERING

{own action-category table: completed count, total signed gain, conditional
expected next yield and uncertainty/unavailable reason, uncompleted attempts}
{current continuation band and threshold, separately from duration expectations}
{necessary specific previous attempts, original request/receipt operands,
actionable failure or qualification, currently received result/handoff facts}
```

The following small **exact fact example** comes from retained `launch_api` call 1 in the closed MSA Workflow. It is not a claim that the original provider sent this proposed text. The original call used the JSON fallback. The retained run used native byte examples served by controlled HTTP and scripted decisions, with no live BV-BRC or new native scientific execution.

```text
Assigned request
Service: bvbrc_appservice. Resource: selected-api. Application: MSA.
Endpoint: usable_handoff. Parent constraints: none supplied.
Aligner: Mafft. Alphabet: dna. Strategy: auto.
Output path: /synthetic/work/output. Output file: selected.
Input members and supplied characters:
| Member | Supplied characters |
| m1|example | AACGT-- |
| m2|example | AATGTT- |
| m3|example | --CGTAA |
| m4|example | A-CGTAA |

STEERING

| Own action | Completed | Total signed gain | Expected next yield | Uncertainty |
| api.bvbrc_appservice.prepare | 1 | 0 | unavailable | category fit not supplied by this legacy call |

| Continuation | Expected next gain | Uncertainty | Cost |
| After 1 completed action | unavailable | insufficient observations | 0.1 |

Preparation: completed; parse status ok; application MSA.
Handoff ready: false. Native job handle: unknown. Result available: false.
Submission operand: preparation_receipt_ref = source_6006eac3880585e7197815ec.
Qualifications: deployment not verified; output path/file references unverified;
input contents and reference release unverified.
```

The expected category value above is deliberately unavailable: the retained call used the legacy protocol and supplied no `action_yields`. The current controller's numeric `-1` sentinel is rendered as insufficient observations, not a negative prediction. The zero total gain is the recorded completed preparation observation. The explicit preparation receipt is retained because it is an actual required submission operand, unlike run IDs or frame hashes.

This example intentionally prints the detailed task narrative and a compact fact table while naming the required expansion blocks. It is **not** a shortened, executable replacement for the full expanded TASK; no production renderer or settled template is claimed.

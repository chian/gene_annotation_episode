# Next GenomeComparison integration boundaries

The current A/B1/B2/B3/B4 pure path is implemented and verified on synthetic
supplied bytes. This does not complete the full scientific tool or its API path.
Two precise interface gaps can be investigated independently before assigning
their production coding. Neither workload changes existing execution or schema.

## Producer retention and decoded witnesses

Input: retained exact App-GenomeComparison.pl and bidir_best_hits implementation,
native invocation dependencies, actual published output definitions, proposal001
and correction002, current A/B1/B2/B3/B4 inputs and numerical requirements.

Output: an additive proposal identifying exact native report format/version,
input/output argument and byte associations, original input-slot-to-executed-
FASTA evidence, emitted-occurrence mappings where the producer can establish
them, and the minimum actual producer retention changes needed. Each field must
name the producing code point or explicit unavailable dependency. A source
locator, claimed validated flag, caller assertion or synthetic scientific report
cannot supply missing execution facts. Preserve complete directional outputs,
search limits and failures. If IDs were collapsed irreversibly, state exactly
where that happens and what can still be retained prospectively.

This proposal determines the future source-specific reader/witness API; it does
not promote current unqualified links or invent a deployed service version.
Owned artifacts: a new dedicated verification/proposal directory only. No edits
to permanent retained source, production code, library, schemas or original run.

## Existing API result-path integration contract

Input: complete existing AppService primitive execution/artifact acquisition,
bundle providers and typed-return consumers, current GenomeComparison service
definition and scope row, actual A/B1/B2/B3/B4 signatures and closed schemas.

Output: an additive concrete wiring proposal naming exact selected operation,
native artifact selectors/formats, explicit supplied-data values, parameters,
source/task associations, provider invocation/return/failure shapes, requested
fact families, actual receiving functions and end-to-end verification cases.
Use the existing API, results and scientific episode boundaries. Never infer a
source/sequence join, restore root tools, add a grading episode or hide new work
inside retrieval. Full reports/witnesses remain separately named dependencies;
legacy descriptive numbers must retain their limited meaning.

Dependencies are the actual pure-function output shapes and the existing host's
typed API, not completion of the other proposal. It must identify precisely
which eventual facts need the new producer contract. Owned artifacts: a separate
new verification/proposal directory only. Production coding starts after root
has checked the actual proposed signatures, consumers and ownership boundaries.

Both fresh workers receive the full immutable goal and must reread its objective
and all sixteen design principles after substantial source examination and
before submitting their proposal. Proposals cannot alter the goal or establish
completion. Shared execution files remain unchanged for the original live test.

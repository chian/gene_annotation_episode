# Required Launch connection checks

These are unexecuted candidate tests for this axis's four HPC-nested Launch
homes. Required helpers, wrappers and assets remain under application test
directories, not runs. Root owns execution and chooses the serial launcher.

Each fixture creates an actual Store problem and Journal, constructs the full
axis registry (A107: 31 owners including API; A110: 27 without API), and invokes
actual HPC planning against retained queue observations. Its selected assignment
and manifest come from the real ledger. The command in the shared mathematical
commission is deliberately unlaunchable. No model, HTTP, SSH, PBS or native
process is invoked.

The helper imports only the data/contract helper
root/tests/hpc_prediction_inputs.py. Its required inputs are the three JSON
observations under root/tests/fixtures/hpc_prediction and
examples/aurora_execution_resources.json.
Their historical queue content supplies contract operands, not a claim about
current live Aurora. The scientific instruction/tool library descriptors are
controlled empty ports; these checks do not interpret scientific evidence.

Real boundaries exercised:

- Parent planning and shared allocation ledger; frozen plan request, reservation,
  independent Launch/native admission, exact caller form, original operation key,
  closed reservation replay and a changed request's rejection.
- Actual runtime action schema and selected-child dispatch. Child execution is
  replaced by a returned builder proxy after request validation/admission.
  Missing handoff fields must fail before either preparation or acquisition.
- Actual runtime tool dispatch into the selected Launch binding and task. The
  task's acquisition/projection tests create a source without its constructor;
  the separate Workflow.build check exercises the actual selected constructor.
  Controller return is a recorded index/credit port, not a scientific stopping
  controller or whole-loop autonomy claim.
- Failed/unavailable returned operations use an explicit transport-result port.
  Invalid arguments execute the real Launch operation. Original measurements
  and action identities survive replay. New waits/reasons are refused; an
  already completed saved wait retains its original credit without new work.
- Full saved pending provider request, original assignment, plan manifest,
  resource configuration, schema, response and replay. A controlled provider
  records all arguments; private presentation is checked against the same-axis
  HPC renderer. No provider service runs.
- Native typed report facts are read from actual initialized, unexecuted native
  state. Receipt/progress effects are recorded ports. The recorded-admission
  cache is controlled to distinguish original admission reuse from new delivery.
  Original child identity, source index, timing-receipt difference and redelivery
  remain real journal contracts.
- Operational handoff counting uses controlled authenticated receipt/usable
  target inputs, two physical attempts of one original resource request, and the
  real credit function. It proves counting semantics, not native receipt custody.
- Parent descriptor hashing reads actual source files. A monkeypatched read
  adds bytes in memory for one selected Launch dependency; no source file is
  changed by the test.

Baseline-compatible behavior tests are enumerated in
runs/hpc_allocation_messages_20261111_a107_a110_preparation/launch_review/run_connected_checks.py.
That phase excludes final-only private task/message/fingerprint assertions.
The connected phase includes everything after root applies repairs and splits.
Known original defects must be retained as failures, not marked as passes or
hidden behind xfail. The full registry assertion remains a diagnostic until the
independently baselined callback-ownership repair is validated.

This suite does not establish complete saved-workflow restoration, authenticated
historical artifact reopening, scientific findings, real native success, or
whole-workflow completion. Those remain distinct root validation scopes.
